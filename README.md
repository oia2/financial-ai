# Financial AI

Платформа для AI-assisted управления инвестиционным портфелем и торговли на российском
фондовом рынке.

Система развивается поэтапно. Первая фича — **Investment Account State**: получение
актуального состояния инвестиционного счёта из T-Bank Invest API, сохранение его во
внутреннем хранилище и отображение в веб-интерфейсе.

---

## Статус

Стек поднимается целиком и работает на живых данных: состояние счёта читается из T-Bank
Invest API, рыночные данные — с MOEX ISS, ранжирование выполняется автоматически по мере
готовности данных.

| Фича | Что даёт |
|---|---|
| 001 Investment Account State | Состояние счёта из T-Bank Invest API |
| 002 Daily ML Emulator | Заглушка звена ранжирования и контракт запроса |
| 003 MOEX Data Ingestion | Ежедневный сбор рыночных данных и неизменяемые наборы |
| 004 Market Data Catchup | Догон пропущенных торговых сессий |
| 005 Market Data Control | Сводка полноты и управляемый догон |
| 006 Market Data UI | Раздел «Рыночные данные» и общая навигация |
| 007 Daily ML Lifecycle | Жизненный цикл ранжирования, доведение данных до последней закрытой сессии, план портфеля |

Каждая фича разрабатывается в отдельной ветке по правилам
[конституции](.specify/memory/constitution.md); её документы — в `specs/<номер>-<имя>/`.

**Звено ранжирования — эмулятор.** Скоры вымышлены, модели за ними нет, и интерфейс
говорит об этом на самом результате. Замена эмулятора настоящей моделью не требует
изменений в планировщике, записи прогонов, хранении, интерфейсе, догоне и повторах.

**Система не торгует.** Ранжирование и план портфеля — утверждения о желаемом составе
счёта: заявки не выставляются, брокерский токен выдан только на чтение.

> **Токен** задаётся в `deployments/docker-compose/.env` **без кавычек**: значение в
> кавычках уходит к брокеру вместе с ними и отклоняется как недействительное.

## Целевая архитектура

```text
рыночные и справочные данные
        ↓
     Daily ML  →  ранжирование активов  →  portfolio / target-position logic
                                                      ↓
                                          Intraday Execution ML
                                                      ↓
                                              исполнение сделок  →  брокер
                                                                      ↓
                                        Backend / PostgreSQL / Frontend
```

Наличие компонента на целевой диаграмме не означает, что он реализуется сейчас.
В объём первой фичи входят только выделенные ниже контейнеры.

Полное описание системы — состав контейнеров, взаимодействия, границы ответственности и
отступления развёртывания от диаграммы — в [`docs/architecture.md`](docs/architecture.md).
Каноническая диаграмма контейнеров: [`docs/container-diagram.svg`](docs/container-diagram.svg).

Звено **Daily ML** ранжирует акции по ожидаемой избыточной доходности против индекса
MOEX на горизонте семи торговых сессий. Модель разрабатывается в отдельном
исследовательском репозитории и находится в исследовательской стадии; её описание —
[`docs/daily-ml-model.md`](docs/daily-ml-model.md).

В платформе это звено пока не реализовано. Чтобы стенд можно было поднимать целиком, в
репозитории есть его эмулятор — отдельный контейнер, который отвечает на запрос
ранжирования правдоподобным по форме ответом с вымышленными скорами. Он ни с чем не
связан и подлежит замене настоящей моделью: см.
[`daily-ml-emulator/README.md`](daily-ml-emulator/README.md).

### Контейнеры первой фичи

| Контейнер | Роль | Ходит в T-Bank |
|---|---|---|
| **frontend** | React-приложение; внутри образа nginx отдаёт статику и проксирует `/api` на backend-api | нет |
| **backend-api** | Публичный HTTP API: отдаёт сохранённое состояние счёта, статус синхронизации, настройку интервала; транслирует команду ручного обновления в worker | **нет** |
| **backend-worker** | Синхронизация с T-Bank Invest API по расписанию и по требованию, преобразование в доменную модель, запись в PostgreSQL | **да, единственный** |
| **postgres** | Последнее успешное состояние счёта, статус синхронизации, настройка интервала | нет |

Поток данных:

```text
T-Bank Invest API → backend-worker → PostgreSQL → backend-api → frontend
```

Ручное обновление:

```text
frontend → backend-api → (внутренний REST) backend-worker → T-Bank Invest API
```

Внутренний REST worker'а наружу не проксируется. Токен доступа к брокеру передаётся
**только** контейнеру `backend-worker`.

## Стек

### Backend

| Задача | Решение |
|---|---|
| Язык | Python 3.12 |
| HTTP API (публичный и внутренний) | FastAPI |
| Валидация, схемы, конфигурация | Pydantic v2, pydantic-settings |
| ORM / миграции | SQLAlchemy 2.0 (async), Alembic |
| Драйвер БД | asyncpg |
| Клиент T-Invest API | `t-tech-investments` (индекс T-Bank, см. ниже) |
| Фоновая синхронизация | asyncio-цикл с интервалом из БД |
| HTTP-клиент backend-api → worker | httpx |
| Менеджер пакетов | uv |

`backend-api` и `backend-worker` собираются из одного Python-пакета `backend/` с двумя
точками входа и разворачиваются как два контейнера.

### Frontend

| Задача | Решение |
|---|---|
| Язык и сборка | TypeScript, React 19, Vite, Node 22 LTS |
| Архитектура | Feature-Sliced Design |
| Server state, polling | TanStack Query |
| Таблица позиций и сортировка | TanStack Table |
| Менеджер пакетов | pnpm |
| Маршруты разделов | свой модуль на History API: разделов два, библиотека роутера не заводится |
| Источник дизайна | Open Design, проект «Портфель FINANCIAL AI» |

### Инфраструктура

PostgreSQL 17, Docker Compose, nginx (внутри образа frontend).

## Конфигурация

Все секреты и зависящие от окружения значения передаются через переменные окружения.
Реальные значения — в `deployments/docker-compose/.env`, который **не коммитится**.
Шаблон без значений — `deployments/docker-compose/.env.example`.

| Переменная | Кому нужна | Назначение |
|---|---|---|
| `TBANK_INVEST_READ_TOKEN` | **только** backend-worker | Персональный токен Т-Банк Invest с правами **только на чтение** |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | postgres | Учётные данные БД |
| `DATABASE_URL` | backend-api, backend-worker | Подключение к PostgreSQL |
| `WORKER_INTERNAL_URL` | backend-api | Адрес внутреннего REST worker'а |
| `DAILY_ML_EMULATOR_PORT` | daily-ml-emulator | Порт эмулятора ранжирования на хосте (по умолчанию 8100) |
| `MARKET_DATA_*` | backend-worker | Сбор рыночных данных MOEX: включение, время запуска после закрытия сессии, глубина первичной загрузки, глубины окон, срок хранения наборов, догон пропущенных сессий, темп обращений к источнику позиций. Секретов среди них нет — данные MOEX ISS публичны |
| `MARKET_DATA_STARTUP_RECOVERY_MAX_SESSIONS` | backend-worker | Предел автоматического восстановления разрыва в сессиях. По умолчанию `0` — без предела, на всю глубину окна догона. Положительное число задаёт предел; разрыв сверх него не собирается вовсе и закрывается управляемым догоном |
| `MARKET_DATA_RETRY_AFTER_MINUTES` | backend-worker | Через сколько минут повторять сессию, сбор которой не удался (по умолчанию 15). Тик планировщика — раз в минуту, и без выдержки устойчивая ошибка даёт шестьдесят обращений в час |
| `MARKET_DATA_SESSION_MAX_ATTEMPTS` | backend-worker | Сколько раз автоматический сбор пытается закрыть одну сессию (по умолчанию 5). Исчерпав предел, сессия остаётся управляемому догону |
| `DAILY_ML_URL` | backend-worker | Адрес звена ранжирования |
| `DAILY_ML_ENABLED` | backend-worker | Считать ли ранжирование автоматически по готовности данных |
| `DAILY_ML_REQUIRED_DATA_GROUPS` | backend-worker | Группы, образующие **обязательный** вход модели. Без их полноты прогон не запускается ни при каких условиях. Дивидендов в перечне нет: они не признак и запрещены как ex-ante |
| `DAILY_ML_MAX_ATTEMPTS`, `DAILY_ML_TICK_SECONDS` | backend-worker | Предел повторов прогона и период проверки готовности |
| `DAILY_ML_EMULATOR_MODEL_ID`, `DAILY_ML_EMULATOR_MODEL_VERSION` | daily-ml-emulator | Идентичность звена. Версия входит в ключ идемпотентности прогона |
| `DAILY_ML_EMULATOR_LATENCY_SECONDS` | daily-ml-emulator | Имитация длительности инференса (по умолчанию 2 с). Без неё состояние «выполняется» не наблюдаемо |

Правила:

- токен создаётся с правами только на чтение — система не инициирует торговых операций;
- токен не вводится в интерфейсе, не хранится в БД и не попадает в логи и ответы API;
- номер брокерского договора отображается только в маскированном виде.

## Запуск

### Docker Compose

```bash
cp deployments/docker-compose/.env.example deployments/docker-compose/.env
# заполнить TBANK_INVEST_READ_TOKEN и POSTGRES_PASSWORD

docker compose -f deployments/docker-compose/docker-compose.yml up --build
```

Интерфейс: <http://localhost:8080>

Проверка живости:

```bash
curl -s localhost:8080/api/health
```

Каждый вечер после закрытия торговой сессии `backend-worker` забирает с MOEX данные
прошедшего дня, складывает их в PostgreSQL, собирает из накопленной истории неизменяемый
набор и запрашивает у звена ранжирования порядок активов. Те же шаги доступны вручную:

```bash
docker compose … exec backend-worker python -m financial_ai.market_data.cli run --session 2026-08-28
docker compose … exec backend-worker python -m financial_ai.ranking.cli rank --asof 2026-08-28
```

#### Ранжирование выполняется само, по готовности данных

Цепочка одна для трёх случаев — обычный вечерний прогон, восстановление после
перезапуска и разбор накопившегося отставания:

> сессия закрылась → данные собраны → **полнота обязательного входа проверена** →
> собран неизменяемый набор → создан прогон → получено ранжирование → результат
> сохранён → дата успешного ранжирования продвинулась.

Три правила, на которых она держится:

- **дата данных и дата модели — разные величины.** Их расхождение и есть отставание;
  свести их в одну означало бы спрятать его;
- **уже посчитанное не пересчитывается.** Прогон опознан датой решения, дайджестом
  набора, моделью и её версией; успешный прогон с тем же ключом — это отсутствие работы,
  а не повод считать заново;
- **на неполном обязательном входе прогон не запускается** ни при каких условиях.

«Проверить сейчас» в разделе «Ранжирование» запускает ровно эту проверку — это **не**
принудительный пересчёт и **не** обращение к бирже: действие смотрит на уже собранное.

Ежедневный сбор идёт по плану из десяти источников (`market_data/plan.py`); дивидендов в
нём больше нет — их никто не читал, а прогон платил за них обращением к брокеру по каждой
бумаге. Семь источников идут на каждую сессию, три — раз в сутки: торговый календарь и
справочники текущего состояния (секторы; лоты, ISIN и вид бумаги — акция или фонд). С
22.06.2026 фонды торгуются на доске акций: сводка показывает их отдельными группами
«котировки фондов» и «агрегаты фондов» с окном от этой даты, и во вход модели они пока
не идут (spec 008, FR-060). У справочников оси сессий нет, ответ один и
тот же, каким бы днём его ни спросили, и при отставании в восемьдесят сессий посессионный
порядок платил за них сто шестьдесят обращений, переписывая одни и те же строки.
Торговый календарь спрашивается после биржевого порога (23:59 МСК) и переспрашивается с
интервалом повтора, пока закрытый день не подтверждён; неудачный запрос выдерживает тот
же интервал (FR-040b, FR-040d). Дальше последней даты календаря сбор не уходит: объявление календаря (`market_data/calendar_spec.py`)
перенесено из `configs/calendars/moex_daily.yaml` исследовательского репозитория.

Недостающей считается любая закрытая сессия, за которую хотя бы один обязательный источник
не отработал успешно, — и отставание границы, и пропуск **внутри** окна, и день, у которого
котировки прошли, а что-то ещё упало. Наличие котировок собранностью не является. Прежде искалось только первое, и дыра посреди истории
не закрывалась никогда. Незакрытая сессия не собирается ни автоматически, ни по кнопке:
дневные бары внутри сессии ещё меняются. Сессия, сбор которой не удался, повторяется не
раньше `MARKET_DATA_RETRY_AFTER_MINUTES`.

Автоматический сбор останавливается и возобновляется из раздела «Рыночные данные», без
перезапуска системы. Это **не** пауза ранжирования: переключатели разные, и один другой не
заменяет. Состояние живёт в процессе сборщика — перезапуск возвращает сбор в работу.
Управляемый догон остановке не подчиняется: это явная команда человека.

#### План портфеля

Раздел «План портфеля» доводит ранжирование до практического ответа: правило
распределения задаёт веса, ранжирование — состав, текущие позиции и деньги счёта —
разницу. Считает `backend-api`: все входы уже в хранилище.

Границы, о которых раздел говорит прямо:

- цена — **закрытие названной торговой сессии**, а не текущая котировка;
- количество выражается целым числом лотов; размер лота приходит с биржи, а не от
  брокера. Остаток округления остаётся деньгами и между активами не перераспределяется;
- облигации и денежный фонд планом не затрагиваются;
- **расчёт портфель не меняет и заявок не выставляет.** Действий исполнения в разделе
  нет.

#### Догон истории запускает человек

Если worker не работал несколько дней, историю он **сам не добирает**. Так сделано после
прогона на живых данных: неуправляемый догон ушёл на 2909 обращений к бирже без спроса и
без возможности вмешаться. Ежедневный цикл собирает текущую сессию, историю добирает
человек — и видит ход, может остановить и продолжить.

```bash
# что собрано и что собрано ПУСТЫМ — по группам источников
docker compose … exec backend-worker python -m financial_ai.market_data.cli coverage

# какие сессии окна не собраны
docker compose … exec backend-worker python -m financial_ai.market_data.cli gaps

# запустить: можно выбрать группы и диапазон, по умолчанию — всё окно
docker compose … exec backend-worker python -m financial_ai.market_data.cli catchup     --group quotes --group aggregates --from 2026-06-01 --till 2026-08-28

# ход работы и мягкая остановка
docker compose … exec backend-worker python -m financial_ai.market_data.cli catchup-status
docker compose … exec backend-worker python -m financial_ai.market_data.cli catchup-stop
```

#### Адресный ремонт подтверждённых пробелов

Перед ручным восстановлением сначала выполняется аудит, затем сохраняется план с явным
лимитом физических HTTP-попыток. Создание плана внешних запросов не делает; повторный
`repair-run` продолжает тот же план, а увеличить лимит можно только отдельной командой.

```bash
docker compose … exec backend-worker python -m financial_ai.market_data.cli repair-audit \
    --from 2026-05-27 --till 2026-09-18 --source futures_positions
docker compose … exec backend-worker python -m financial_ai.market_data.cli repair-plan \
    --from 2026-05-27 --till 2026-09-18 --source futures_positions --request-budget 6500
docker compose … exec backend-worker python -m financial_ai.market_data.cli repair-run --plan-id <UUID>
# Только после осознанного решения расширить бюджет:
docker compose … exec backend-worker python -m financial_ai.market_data.cli repair-extend \
    --plan-id <UUID> --request-budget 9000
```

Недоступный после серии неудач источник больше не опрашивается впустую до конца одного
прогона, но для каждой непройденной сессии сохраняется `failed` с причиной. Поэтому
неполнота остаётся видна в аудите и не выдаётся за успешный сбор.

То же самое доступно **из интерфейса**: раздел «Рыночные данные» показывает сводку и ведёт
догон — запуск с выбором групп и диапазона, ход работы, остановка и продолжение. Команда
остаётся: она удобнее в сценариях эксплуатации и не требует браузера.

Команда — **тонкий клиент**: сбор идёт фоновой задачей в `backend-worker`, а команда
обращается к его внутреннему интерфейсу. Интерфейс подключён к тому же каналу, но через
публичные маршруты `backend-api` (`/api/market-data/*`), которые передают ему четыре
операции: чтение сводки, чтение состояния прогона, запуск и остановку. Наружу внутренний
интерфейс worker'а не выставляется — у его контейнера нет проброса портов, а nginx его не
проксирует. Поэтому «следить» не означает «не закрывать
терминал», а остановка мягкая: начатая сессия доводится до конца, следующая не начинается.
День, собранный наполовину, неотличим от собранного полностью — обрывать его нельзя.

Состояние задания живёт в процессе worker'а и вместе с ним исчезает: после перезапуска
`catchup-status` отвечает `idle`. Зависшего «идёт» не бывает по устройству, а что собрано
на самом деле — видно по данным. **Как прошёл сбор — переживает перезапуск**: журнал
прогонов (`/api/market-data/runs`) читается из таблицы исходов, а не из памяти процесса.
Рядом идут изменения состава инструментов: появление фьючерса, смена семейства контрактов,
исчезновение инструмента. Без них рост или убыль числа собранных бумаг выглядели бы
пропуском сбора.

Сводка `coverage` показывает **два числа на группу**: покрытие в сессиях и долю строк со
значениями. Одного было бы мало: позиции по фьючерсам однажды имели покрытие 224 сессии из
224 при пяти непустых строках на 57 029, и отчёт по покрытию объявил бы группу собранной.

Сводка называет и **состав бумаг**: сколько их и у скольких есть фьючерс. Неполнота группы
позиций перестаёт быть догадкой — фьючерс есть не у каждой бумаги, и его отсутствие не
пропуск. Полнота группы считается по **каждому** источнику: успех одного не закрывает
пропуск другого, и раскрытие группы называет источник поимённо. Наблюдения при этом тоже
считаются по источнику: у «глобальных рядов» одна таблица на четыре источника, и ряд ЦБ за
сессию не закрывает её ни Brent, ни индексу, ни рядам ISS.

На **пустом** хранилище окно модели загружается тем же ручным сбором всех групп за всё
окно — проверяемым путём с доказательствами полноты; отказа «нужна первичная загрузка»
больше нет. Команда `backfill` остаётся необязательной загрузкой глубокой истории котировок
по бумагам: состав доски она берёт у биржи, продолжается по доказательству уже загруженной
истории бумаги (а не по её наличию в справочнике) и не заходит дальше последней закрытой
сессии. Полноту доски за дату она не подтверждает.

Сессия закрыта источником, когда сохранены **доказательства всех его единиц работы**, а не
по статусу прогона: поздняя неудача не отменяет доказанную дату, диапазон продолжается по
недоказанному остатку, а каждый источник спрашивается только в своём окне (позиции — 82
сессии, даже когда выбраны все группы). Незавершённость хранится с причиной — источник,
остановка, перезапуск, сбой обработки, — и «ошибкой источника» экран называет только первую.

#### Сверка источников с живыми ответами

Разбор чужих страниц тесты подтверждают на образцах, а образец воспроизводит то, что мы
про источник думаем. Поэтому есть отдельные команды, обращающиеся к источнику
по-настоящему. В `scripts/check.sh` они **не входят**: сеть в среде сборки недоступна, и
гейт стал бы недетерминированным.

```bash
docker compose … exec backend-worker python -m financial_ai.market_data.cli verify-cbr --session 2026-09-02
docker compose … exec backend-worker python -m financial_ai.market_data.cli verify-brent --session 2026-08-28
docker compose … exec backend-worker python -m financial_ai.market_data.cli verify-positions --session 2026-08-28
docker compose … exec backend-worker python -m financial_ai.market_data.cli verify-reference --session 2026-09-02
```

Сессии, которые догнать не удалось, доезжают до модели объявлением полноты окна в запросе.
Без него неполнота входа была бы неотличима от решения модели, и выпавший из ранжирования
актив выглядел бы исключённым ею.

Вместе со стендом поднимается эмулятор Daily ML — заглушка звена ранжирования. Его можно
запустить и отдельно, он ни от чего не зависит:

```bash
docker compose -f deployments/docker-compose/docker-compose.yml up --build daily-ml-emulator
curl -s "localhost:8100/rankings?decision_date=2026-08-28"
```

Все скоры в его ответе вымышлены; каждый ответ помечен `"emulated": true`.

### Локальная разработка

```bash
# PostgreSQL
docker compose -f deployments/docker-compose/docker-compose.yml up postgres

# backend
cd backend
uv sync
uv run alembic upgrade head
uv run uvicorn financial_ai.api.app:app --port 8001 --reload      # backend-api
uv run uvicorn financial_ai.worker.app:app --port 8000 --reload   # backend-worker

# frontend
cd frontend
pnpm install
pnpm dev            # проксирует /api на backend-api, nginx не нужен
```

### Установка SDK T-Invest

Пакет `t-tech-investments` **не устанавливается с публичного PyPI** — там он на карантине
и не содержит файлов. Нужен индекс T-Bank:

```bash
pip install t-tech-investments==1.49.3 \
  --extra-index-url https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple
```

Индекс зафиксирован в `backend/pyproject.toml`, поэтому `uv sync` делает это сам.

## Проверки качества

Фича не считается завершённой, пока все применимые проверки не проходят.

```bash
scripts/check.sh                # полный гейт, включая сборку образов
scripts/check.sh --no-docker    # быстрый цикл разработки, НЕ полный гейт
```

Скрипт прогоняет линтеры, форматирование, типы, тесты обоих компонентов,
миграции на свежесозданной БД, сборку frontend с проверкой статических файлов
и сборку docker-образов. Запускать проверки
по частям не следует: именно частичные прогоны пропускали дефекты.

Backend-тесты гейт раскладывает по шардам (`scripts/pytest_shards.py`), у каждого своя
тестовая база `<имя>_test_<n>`; число шардов — `PYTEST_SHARDS` (по умолчанию до 6,
каждый держит около десяти соединений PostgreSQL). Эмулятор и frontend проверяются
параллельно с backend. Состав проверок от этого не меняется; пропуск тестов с БД
считается провалом гейта.

## Процесс разработки

Проект ведётся по spec-driven подходу на базе [Spec Kit](https://github.com/github/spec-kit):
`specify` → `clarify` → `plan` → `tasks` → `implement`.

Обязательные инженерные правила — в [`.specify/memory/constitution.md`](.specify/memory/constitution.md).
Ключевое из них:

- существенная неоднозначность не разрешается предположением — она уточняется и фиксируется
  в спецификации;
- реализация не должна молча противоречить спецификации или утверждённому дизайну: сначала
  правится исходный артефакт;
- каждая фича разрабатывается в отдельной ветке `feature/<описание>` или `fix/<описание>`;
- секреты не попадают в исходный код, репозиторий и логи.

Контекст проекта для AI-агентов — в [`AGENTS.md`](AGENTS.md).
