# Contract: публичные маршруты жизненного цикла Daily ML

Публичная граница раздела «Ранжирование». `backend-api` отдаёт состояние и историю из
хранилища и передаёт команды внутреннему каналу `backend-worker` — тем же способом, каким
уже передаёт синхронизацию портфеля и управление догоном.

Внутренний интерфейс worker наружу не выставляется: у его контейнера нет проброса портов,
и nginx его не проксирует. Аутентификации у публичных маршрутов нет, как и у остальных.

---

## `GET /api/daily-ml/status`

Состояние раздела одним ответом. Не кэшируется.

```json
{
  "status": "waiting",
  "paused": false,
  "latest_data_ready": "2026-09-11",
  "latest_ml_success": "2026-09-11",
  "current": {
    "asof_date": "2026-09-11",
    "started_at": "2026-09-11T17:30:04+00:00",
    "attempt": 1
  },
  "queue": [
    { "asof_date": "2026-09-12", "status": "queued" }
  ],
  "queue_progress": { "completed": 2, "total": 3 },
  "last_error": null,
  "next_check_at": "2026-09-12T16:30:00+00:00",
  "data_gap_sessions": 0,
  "readiness_known": true,
  "blocking_groups": [
    { "group": "aggregates", "title": "агрегаты" },
    { "group": "positions", "title": "позиции по фьючерсам" }
  ],
  "stale_latest": false,
  "model_id": "daily-ml-emulator",
  "model_version": "emulator-v1",
  "emulated": true
}
```

| Поле | Смысл |
|---|---|
| `status` | `up_to_date`, `waiting`, `running`, `lagging`, `failed`, `paused`, `data_gap` |
| `latest_data_ready` | Последняя дата с полным обязательным входом; `null`, если такой нет |
| `latest_ml_success` | Последняя дата с успешным прогоном |
| `current` | Выполняющийся прогон; `null`, если ничего не идёт |
| `queue` | Даты, принятые к обработке, от старой к новой |
| `queue_progress` | Счётный прогресс очереди: обработано `completed` из `total`. Отставание начинается с самой старой даты очереди. Пустая очередь даёт нули |
| `next_check_at` | Ближайший срок, после которого собираются данные завершившейся сессии, в поясе биржи со смещением. **Не** периодичность проверки: ранжирование ищет работу непрерывно. **Не** время начала расчёта |
| `data_gap_sessions` | Насколько отстают данные; `0` — не отстают |
| `readiness_known` | Ответил ли сборщик. `false` означает «готовность неизвестна», и это НЕ то же, что «готовой даты нет» |
| `blocking_groups` | Обязательные группы данных, из-за которых дата не готова: идентификатор и название. Пустой список — вход полон. Считает сборщик, тем же расчётом, что и саму готовность; название приходит оттуда же, что и в сводке рыночных данных, — второго объявления одного факта не заводится |
| `stale_latest` | Для последней готовой даты вход изменился после успеха. `null` — не рассчитан: сборщик до этого вопроса не дошёл или не ответил |
| `emulated` | Результаты получены эмулятором, а не моделью |

**Правило, которое нельзя нарушить**: `next_check_at` — это срок, после которого станут
собираться данные завершившейся сессии. Периодичностью проверки он не является: реконсиляция
идёт по тику планировщика, после каждого успешного сбора, при запуске и по команде человека —
то есть непрерывно. Момент начала расчёта заранее неизвестен, и поля для него в ответе **нет**
намеренно: показать его значило бы выдумать.

Отдаётся со смещением пояса биржи (`+03:00`): срок привязан к закрытию сессии на MOEX, и в
этом поясе он и определён. Показывается он при этом в поясе человека — перевод делает
браузер, второго поля для этого не заводится (FR-073, FR-074).

Момент передаётся целиком, но **на экране от него берётся только час** (FR-054a). Дата в
поле условна: она вычисляется часами, без календаря, и в выходной указывает на день, когда
торгов не было. Полный момент нужен, чтобы браузер верно перевёл час в пояс зрителя с учётом
его перехода на летнее время; сама дата потребителю не показывается.

Доли готовности внутри одной даты в ответе тоже нет, и по той же причине: звено
ранжирования её не сообщает, а полоса, нарисованная по таймеру браузера, была бы выдумкой.
Счётный прогресс очереди — другое дело: это факт о хранилище, и он считается сервером,
чтобы не меняться от перезагрузки страницы.

**Устаревание входа тоже считает сборщик** — и по причине более грубой, чем разделение
обязанностей. Ответ на вопрос «изменился ли вход» требует пересобрать набор целиком, и на
живом стенде это 17 секунд процессорного времени. На маршруте, который интерфейс опрашивает
раз в три секунды, это положило весь `backend-api`: очередь вставала целиком, `/api/health`
отвечал двадцать секунд, состояние не укладывалось в таймаут и отдавало `504`. Сборщик
собирает набор на своём тике ради дайджеста — там ответ уже оплачен, и берётся он оттуда.

**Готовность данных считает сборщик**, а не `backend-api`: перечень обязательных групп и
глубины окон задаются конфигурацией worker'а, и второй счёт по другой конфигурации
разойдётся с первым. Это то же правило, что уже действует для сводки полноты. Расхождение
наблюдалось на живом стенде: раздел показывал «готовых данных нет» рядом с успешным
прогоном ровно за эту дату.

Читается это внутренним маршрутом `GET /internal/daily-ml/state` — он только читает и
заданий не создаёт. Когда сборщик не ответил, история всё равно отдаётся из хранилища, а
`readiness_known: false` говорит, что о готовности сказать нечего.

**Чего не хватает — говорится**, а не подразумевается. «Ожидаются данные» без ответа на
вопрос «каких?» оставляет человека гадать, а расчёт готовности этот ответ уже содержит:
`blocking_groups` перечисляет обязательные группы, в окне которых есть несобранные
сессии.

## `GET /api/daily-ml/runs`

История прогонов, новые сверху. Параметры: `status` (отбор), `limit`, `offset`.

```json
{
  "total": 143,
  "items": [
    {
      "id": 143,
      "asof_date": "2026-09-11",
      "status": "success",
      "model_id": "daily-ml-emulator",
      "model_version": "emulator-v1",
      "attempt": 1,
      "started_at": "2026-09-11T17:30:04+00:00",
      "finished_at": "2026-09-11T17:30:06+00:00",
      "duration_seconds": 2,
      "included_asset_count": 288,
      "error_message": null
    }
  ]
}
```

Признак устаревания в списке **не считается**: он требует пересборки набора и нужен только
при открытии прогона.

## `GET /api/daily-ml/runs/{id}`

Один прогон: вход, исход, результат.

```json
{
  "id": 143,
  "asof_date": "2026-09-11",
  "status": "success",
  "attempt": 1,
  "input": {
    "dataset_digest": "sha256:9f2c…",
    "dataset_ref": "file:///datasets/2026-09-11-9f2c00…",
    "dataset_available": true,
    "window_from": "2025-06-11",
    "window_till": "2026-09-11",
    "complete": true
  },
  "model_id": "daily-ml-emulator",
  "model_version": "emulator-v1",
  "emulated": true,
  "started_at": "2026-09-11T17:30:04+00:00",
  "finished_at": "2026-09-11T17:30:06+00:00",
  "error_code": null,
  "error_message": null,
  "stale": false,
  "items": [
    { "rank": 1, "asset_id": "EQ_AST_SBER", "price_series_id": "EQ_PRS_SBER", "score": "0.996528" }
  ]
}
```

| Правило | Почему |
|---|---|
| `score` — строка | Скор участвует в сортировке; `float` сделал бы порядок зависимым от представления |
| `dataset_available: false` | Набор удалён ретеншеном. Результат остаётся, повтор невозможен |
| `stale` приходит от сборщика, а не считается здесь | Ответ стоит пересборки набора: 314 сессий на 512 активов — секунды процессорного времени. На пути, которого ждёт человек, такой работе не место: она упирается в процессор и держит весь процесс. Сборщик собирает набор на своём тике, и там ответ уже оплачен |
| `stale` бывает `null` | «Не рассчитан» и «не устарел» — разные утверждения. Ответ известен для последней готовой даты; для исторических он не вычисляется, и `false` там было бы выдумкой |
| Модель описана теми же полями, что в списке | Просмотр прогона — это строка истории плюс вход и результат. Вторая форма для тех же двух полей заставила бы потребителя держать два разбора одного факта |
| `window_from`, `window_till`, `complete`, `emulated` читаются из прогона | Это свойства прошлого. Пересчёт по нынешним настройкам и нынешним данным ответил бы на сегодняшний вопрос вчерашней записью |

Список `items` постраничный: параметры `limit` и `offset`.

## `POST /api/daily-ml/reconcile`

Немедленная проверка. **Не** принудительный пересчёт.

```json
{ "queued": 0, "already_up_to_date": true, "message": "всё актуально" }
```

| Исход | Ответ |
|---|---|
| Всё посчитано | `queued: 0`, `already_up_to_date: true` |
| Появились готовые даты без прогона | `queued: N` |
| Данные отстают сильнее предела | `data_gap_sessions: N`, заданий не создано |
| Режим на паузе | `paused: true`, заданий не создано |

Уже успешно обработанный вход пропускается всегда — при перезапуске, тике планировщика,
нажатии человека и повторной реконсиляции.

---

## `POST /api/daily-ml/runs/{id}/retry`

Повтор отказавшего прогона: `attempt` увеличивается, статус возвращается в `queued`.

| Условие | Ответ |
|---|---|
| Прогон не в состоянии отказа | `409 run_not_failed` |
| Входной набор удалён | `409 dataset_expired` — повторить нечем |
| Исчерпан предел попыток | `409 attempts_exhausted` |

---

## `PUT /api/daily-ml/settings`

```json
{ "paused": true }
```

Пауза останавливает создание новых заданий. Выполняющееся задание доводится до конца.
**Сбор рыночных данных пауза не останавливает** — это разные механизмы, и интерфейс обязан
это говорить.

---

## Отказы

| Код HTTP | `code` | Когда |
|---|---|---|
| `404` | `run_not_found` | Прогона с таким идентификатором нет |
| `409` | `run_not_failed`, `dataset_expired`, `attempts_exhausted` | Повтор невозможен |
| `503` | `worker_unavailable` | Сборщик не ответил — это не отказ операции |

Сообщения не содержат технических подробностей, адресов внутренних сервисов и
конфигурации.
