# Implementation Plan: Жизненный цикл Daily ML и план портфеля

**Branch**: `feature/daily-ml-lifecycle` | **Date**: 2026-09-12 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/007-daily-ml-lifecycle/spec.md`

## Summary

Звено ранжирования существует с фичи 002, но жизненного цикла у него нет: функция
`ingest_and_rank` написана и **никем не вызывается**, результат нигде не сохраняется, а
граница данных не движется вперёд без ручного вмешательства. Фича замыкает цикл.

Четыре части работы:

1. **Оркестрация.** Персистентный прогон Daily ML, очередь на таблице, реконсиляция при
   старте и после каждого сбора, идемпотентность по четырём полям, восстановление
   прерванных прогонов.
2. **Данные.** Доведение границы до последней закрытой торговой сессии с ограничением
   автоматического восстановления; перевод планировщика с памяти процесса на сохранённое
   состояние; сбор размера лота в справочник активов.
3. **План портфеля.** Правила распределения из исследования, применённые к последнему
   успешному ранжированию и текущему счёту; расчёт в `backend-api`, целые лоты, остаток в
   деньгах.
4. **Интерфейс.** Разделы «Ранжирование» и «План портфеля», перенесённые из утверждённого
   артефакта Open Design.

## Technical Context

**Language/Version**: Python 3.12 (backend, эмулятор), TypeScript 5.7 / React 19 (frontend)

**Primary Dependencies**: FastAPI, SQLAlchemy, Alembic, httpx, Pydantic; React 19,
`@tanstack/react-query`, `@tanstack/react-table`, Vite. **Новых зависимостей нет**:
очередь строится на таблице и advisory-локе PostgreSQL (research.md, R2).

**Storage**: PostgreSQL 17. Фича добавляет две таблицы и одну колонку — миграция
`0010`.

**Testing**: pytest + respx (контракт, оркестрация), vitest + msw + Testing Library
(фронтенд)

**Target Platform**: контейнеры docker compose; браузеры с поддержкой ES2022

**Project Type**: веб-приложение — `backend/` (два контейнера из одного пакета),
`daily-ml-emulator/`, `frontend/`

**Performance Goals**: проверка планировщика раз в минуту без заметной нагрузки; прогон
ранжирования с эмулятором — единицы секунд; план портфеля считается по сохранённым данным
без обращений наружу

**Constraints**: Daily ML никогда не запускается на неполном обязательном окне; глубокий
исторический догон автоматически не запускается; ни одно действие не обращается к брокеру
на запись; интерфейс знает только публичные маршруты

**Scale/Scope**: около 250 прогонов в год, до 288 строк ранжирования на прогон, 5 групп
данных, 4 состояния прогона, 2 новых раздела интерфейса

## Constitution Check

*GATE: пройден до Phase 0 и перепроверен после Phase 1.*

| Принцип | Как выполняется |
|---|---|
| I. Неоднозначность не разрешается предположением | Пять решений владельца зафиксированы в спецификации до плана. Два открытых вопроса (расчёт плана, источник лота) закрыты чтением исследовательского репозитория, а не догадкой, и записаны с обоснованием |
| II. Простота, качество и расширяемость | Ни одной новой зависимости и ни одного нового сервиса. Очередь — таблица, блокировка — существующий advisory-лок, сбор сессий — существующий `ingest_session`, готовность — существующие `gaps` и сводка. Статусов ровно четыре: пауза принадлежит режиму, устаревание вычисляется, отмена не заводится до появления длинного инференса |
| III. Согласованность спецификации и реализации | Аудит выполнен до плана; расхождения (неподключённый `ingest_and_rank`, память планировщика, отсутствие лота) описаны в спецификации как факты, а не обойдены |
| IV. Обязательные проверки качества | Новая оркестрация покрывается тестами идемпотентности и переходов, план — тестами арифметики, интерфейс — тестами состояний; готовность проверяется `scripts/check.sh` целиком |
| V. Чистота и структура репозитория | Новые модули встают в существующую раскладку: `backend/src/financial_ai/daily_ml/`, `api/routes/`, FSD-слои фронтенда. Новых каталогов верхнего уровня нет |
| VI. Изоляция по веткам | Работа в `feature/daily-ml-lifecycle` |
| VII. Безопасность и конфигурация | Секретов не вводится. Брокерский токен остаётся только у worker; план и ранжирование к брокеру не обращаются. Причина отказа очищается от технических подробностей перед показом |
| VIII. Дизайн-инструмент как источник истины | Оба раздела переносятся из артефакта Open Design; сверка по `data-od-id`, а не по классам — вывод, оплаченный прошлой фичей |
| IX. Актуальность проектной документации | Меняются состав публичных маршрутов, конфигурация и поведение планировщика — `README.md`, `AGENTS.md` и `docs/architecture.md` актуализируются до объявления работы завершённой |

**Результат**: нарушений нет, Complexity Tracking не заполняется.
