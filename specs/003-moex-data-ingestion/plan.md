# Implementation Plan: Сбор рыночных данных MOEX и передача их в Daily ML

**Branch**: `feature/moex-data-ingestion` | **Date**: 2026-08-29 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/003-moex-data-ingestion/spec.md`

## Summary

`backend-worker` получает второй род занятий: помимо синхронизации счёта с брокером он
начинает собирать рыночные данные с MOEX. Раз в торговую сессию, после её закрытия,
worker забирает данные завершившейся сессии одним запросом по дате, кладёт их в
PostgreSQL инкрементально, материализует неизменяемый набор входных данных на дату
решения и вызывает звено ранжирования, передавая ссылку на набор и его дайджест.

Ключевые числа выведены из кода исследовательского репозитория, а не назначены: глубина
окна — **314 торговых сессий** для цен и глобальных рядов, **82** для позиций (см.
[research.md §1](./research.md)). Именно эта глубина сделала передачу рядов в теле
запроса непрактичной — 5,9 МБ при 0,3% новых данных — и определила переход на ссылку с
дайджестом.

Технический подход: существующий стек `backend/` без новых инструментов. Парсеры
переносятся из `MR-MASTER-DRO` с фиксацией происхождения; инженерия признаков **не**
переносится и остаётся на стороне модели.

## Technical Context

**Language/Version**: Python 3.12 — тот же пакет `backend/`, что и сейчас

**Primary Dependencies**: FastAPI и SQLAlchemy 2.0 (async) уже есть; добавляется
HTTP-клиент к MOEX ISS. `httpx` уже в зависимостях `backend/` — второй HTTP-библиотеки не
вводится. Исходные парсеры используют `requests`; при переносе клиент адаптируется под
`httpx`, поведение повторов сохраняется.

**Storage**: PostgreSQL 17 для собранных данных; неизменяемые наборы — файлы на томе,
общем для `backend-worker` и звена ранжирования

**Testing**: pytest, уже настроен в `backend/`; для обращений к бирже — `respx`, тоже уже
в зависимостях

**Target Platform**: Linux-контейнеры в существующем `docker-compose`

**Project Type**: расширение существующего контейнера `backend-worker` плюс изменение
контракта контейнера `daily-ml-emulator`

**Performance Goals**: ежедневный добор — одно обращение к бирже на источник; полный цикл
после закрытия сессии укладывается в минуты. Первичная загрузка истории — часы, разово,
частями.

**Constraints**: точность цен (`Decimal` → `NUMERIC(28,9)` → строки в JSON); отсутствие
секретов у звена ранжирования; календарь как единственный гейт дат; запрет на
передатирование запоздавших наблюдений.

**Scale/Scope**: около 288 активов, 14 источников, глубина истории — вся доступная при
первичной загрузке. Объём кода оригинала — около 8000 строк; переносится подмножество,
относящееся к получению и разбору данных.

## Дополнение к канонической диаграмме

Материализованный набор входных данных лежит на томе, доступном и `backend-worker`, и
звену ранжирования. На диаграмме такой связи нет.

Это **не** обход запрета «звено ранжирования не ходит в хранилище»: набор неизменяем,
опознан дайджестом и не является базой данных — ни схемы, ни реквизитов доступа, ни
возможности молча измениться. Именно так модель работает и сегодня, читая неизменяемый
снапшот.

Диаграмма — канон, поэтому её нужно дополнить в draw.io: связь
`Backend-Worker → набор входных данных → Daily ML`. До внесения правки расхождение
зафиксировано здесь и в `docs/architecture.md`.

**Structure Decision**: код ложится внутрь существующего пакета `backend/` двумя
подпакетами — `market_data/` (сбор) и `ranking/` (обращение к модели). Отдельный
контейнер не заводится: по канонической диаграмме в MOEX ходит `backend-worker`, и
разделение на два процесса добавило бы сервис, не решая ни одной задачи.

Разделение внутри `market_data/` на `iss/`, `sources/` и `repository.py` продиктовано
переносом: у каждого источника своя логика разбора, но общий клиент и общая запись.
`PROVENANCE.md` рядом с кодом — чтобы происхождение не отрывалось от того, что оно
описывает.

## Порядок работ: три среза

Спецификация не сокращается — сокращается длина шага до первой проверяемой точки.
Обоснование в [research.md §9](./research.md).

| Срез | Содержание | Проверяемый результат |
|---|---|---|
| **A** | календарь, котировки D1, схема хранения, планировщик, материализация набора, контракт запроса, приём контракта эмулятором | Цепочка `биржа → БД → набор → ранжирование` работает целиком |
| **B** | агрегаты, индексы и их дневной состав, USD, ключевая ставка, ЗКЦ, Brent | Глобальные ряды в наборе |
| **C** | позиции по фьючерсам, секторы, дивиденды | Задержанное прибытие и маски |

Срез A самодостаточен: он один даёт работающую сквозную систему. B и C добавляют
источники, не меняя ни границ, ни контракта, ни схемы.
