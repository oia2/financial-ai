# Data Model: Сбор рыночных данных MOEX

Схема хранения собранных данных и структура неизменяемого набора, передаваемого звену
ранжирования. Контракт запроса — в
[contracts/daily-ml-request.md](./contracts/daily-ml-request.md), перечень источников —
в [contracts/moex-sources.md](./contracts/moex-sources.md).

---

## 1. Общие правила

Действуют для всех таблиц раздела.

| Правило | Как обеспечивается |
|---|---|
| Точность цен | `Decimal` в домене, `NUMERIC(28,9)` в БД, строки в JSON. `float` на пути «биржа → БД → набор» запрещён |
| Отличие пропуска от нуля | Отсутствующее значение хранится как `NULL`. Нулём не заполняется, соседними сессиями не достраивается |
| Идентичность | Наблюдение несёт и `asset_id`, и `price_series_id`: один актив может иметь несколько несшиваемых рядов |
| Ось дат | Любая дата наблюдения принадлежит торговому календарю. Дат вне календаря в рыночных таблицах не бывает |
| Инкрементальность | Повторная запись за ту же дату и тот же ключ обновляет, а не дублирует |

## 2. Торговая сессия

Ось всего остального. Заполняется первой, гейтит все прочие источники.

| Поле | Тип | Смысл |
|---|---|---|
| `session_date` | date, PK | Дата торговой сессии на доске TQBR |
| `observed_at` | timestamptz | Когда дата попала в календарь |

**Правила**:

- сессия существует, если в этот день торговалась опорная бумага (по умолчанию SBER) —
  календарь отражает **фактические** торги, а не план;
- дата, которой нет в этой таблице, торговой сессией не является: сбор рыночных рядов за
  неё не выполняется, и «пропуском данных» её отсутствие не считается;
- «предыдущие 314 сессий» отсчитываются по этой таблице, а не по календарным дням.

## 3. Актив

| Поле | Тип | Смысл |
|---|---|---|
| `asset_id` | text, PK | Экономический актив, устойчивый к переименованиям |
| `ticker` | text | Текущий маршрутный ключ для обращения к бирже |
| `first_seen_date` | date | Первая сессия, в которой актив наблюдался |
| `last_seen_date` | date | Последняя наблюдавшаяся сессия |

`ticker` — именно маршрутный ключ, а не идентификатор: при переименовании он меняется,
`asset_id` остаётся.

## 4. Ценовой ряд

| Поле | Тип | Смысл |
|---|---|---|
| `price_series_id` | text, PK | Сшиваемый ценовой процесс |
| `asset_id` | text, FK | Актив, которому принадлежит ряд |
| `first_date`, `last_date` | date | Границы наблюдавшейся истории ряда |

Один `asset_id` может иметь несколько `price_series_id`: переименование сливает ряды,
разрыв истории — нет.

---

## 5. Дневное наблюдение по активу

Котировки TQBR за сессию. Основная по объёму таблица.

| Поле | Тип | Смысл |
|---|---|---|
| `price_series_id` | text, PK | Часть ключа |
| `session_date` | date, PK | Часть ключа |
| `asset_id` | text | Экономический актив |
| `open`, `high`, `low`, `close` | NUMERIC(28,9) | Цены сессии |
| `volume` | NUMERIC(28,9) | Объём |
| `ingested_at` | timestamptz | Когда наблюдение сохранено |
| `source_revision` | text | Отметка версии значения для обнаружения переиздания |

**Ключ**: `price_series_id + session_date`. Именно ряд, а не актив: у актива с несколькими
рядами наблюдения не должны сливаться в одну строку.

**Переиздание значений** (FR-015): биржа иногда исправляет уже опубликованные данные.
Перезапись выполняется, но факт изменения ранее сохранённого значения фиксируется, а не
проходит молча.

---

## 6. Глобальный дневной ряд

Значения, не привязанные к активу: индексы, курс USD, ключевая ставка, ЗКЦ, Brent.

| Поле | Тип | Смысл |
|---|---|---|
| `series_id` | text, PK | Идентификатор ряда, например `IMOEX`, `USD_CBR`, `KEY_RATE` |
| `session_date` | date, PK | Часть ключа |
| `value` | NUMERIC(28,9) | Значение |
| `ingested_at` | timestamptz | Когда сохранено |

Режим доступности у рядов различается и учитывается при сборе: рыночные ряды доступны
после закрытия сессии, макроряды ЦБ — до закрытия и уже относятся к этой сессии.

---

## 7. Результат прогона сбора

Без этой таблицы «собралось ли всё» пришлось бы выяснять по логам.

| Поле | Тип | Смысл |
|---|---|---|
| `run_id` | uuid, PK | Прогон |
| `session_date` | date | Сессия, за которую собирали |
| `source_id` | text | Источник |
| `status` | text | `ok`, `failed`, `skipped` |
| `failure_reason` | text \| null | Причина неуспеха |
| `rows_written` | integer | Сколько наблюдений записано |
| `started_at`, `finished_at` | timestamptz | Границы прогона |

**Правила**:

- `skipped` — законный исход: неторговый день или источник, у которого нет данных на эту
  дату;
- неуспех одного источника не отменяет успех остальных;
- незакрытые источники видны запросом к этой таблице, а не чтением логов.

## 8. Неизменяемый набор входных данных

Материализуется после сбора, передаётся звену ранжирования по ссылке.

| Поле манифеста | Смысл |
|---|---|
| `dataset_ref` | Ссылка на набор |
| `digest` | Дайджест содержимого; одинаковое содержимое даёт одинаковый дайджест |
| `asof_date` | Дата решения, на которую собран набор |
| `windows` | Фактические глубины окон по видам рядов |
| `sessions` | Перечень торговых сессий, вошедших в набор |
| `assets` | Активы, данные которых вошли |
| `materialized_at` | Момент материализации |
| `source_runs` | Прогоны сбора, чьи данные вошли |

**Свойства, ради которых набор существует**:

- **неизменяемость**: после материализации содержимое не меняется. Доезд запоздавших
  данных порождает **новый** набор с новым дайджестом, а не правит старый;
- **опознаваемость**: дайджест вычисляется из содержимого и служит идентификатором входа
  в запросе и ответе;
- **самодостаточность**: набор содержит всё, что нужно для построения признаков на
  `asof_date`, — звену ранжирования не требуется ни база, ни биржа.

**Глубина окон** (выведена из конфигурации признаков модели, см.
[research.md §1](./research.md)):

| Ряд | Сессий |
|---|---|
| Цены | 314 |
| Агрегаты торгов | 314 — то же окно, что у цен |
| Глобальные ряды | 314 |
| Позиции по фьючерсам | 82 |
| Секторы эмитентов | оси сессий нет: справочник текущей принадлежности |

Значения настраиваемы: набор признаков модели может измениться.

**Состав набора** выведен из входов модели, объявленных в
`pipelines/data_plane_step0/pipeline.py:88-103` исследовательского репозитория:

| Файл набора | Содержимое | Почему модели нужно |
|---|---|---|
| `prices.json` | OHLCV по ценовым рядам | `asset_price_core_v1` |
| `aggregates.json` | `value`, `num_trades`, `waprice` | `market.equities_agg` → `data_plane_step4:129` → слой состояния и признаки |
| `global.json` | индексы, `IDX_WEIGHT_*`, USD, ставка, ЗКЦ, Brent | `global_regime_core_v1` |
| `positions.json` | позиции ФИЗ/ЮР по фьючерсам | `asset_positions_core_v1` |
| `sectors.json` | `asset_id → сектор` | `issuer_sector_static` в `data_plane_step6:383`; `sector_relative_windows` |
| `manifest.json` | дайджест, окна, сессии, активы | опознание входа |

**Дивиденды в набор не входят**: `data_plane_step0/pipeline.py:1057` запрещает их как
ex-ante признак, `data_plane_step1/pipeline.py:339` использует только для меток, а
обучение объявлено вне платформы. В хранилище они остаются.

**Правило хранения** (FR-026): наборы неизменяемы и потому накапливаются. Срок хранения
задаётся конфигурацией; без правила очистки место закончится.

## 9. Чего в этой модели нет

Сознательно, чтобы граница не размывалась:

- **признаков** — ни одного. Ни возвратов, ни волатильностей, ни z-оценок. Всё
  производное строится на стороне модели;
- **масок допустимости** — правило допустимости строится тем же конвейером, что и
  признаки, и живёт там же;
- **скоров и ранжирований** — они приходят в ответе и в этой фиче не сохраняются;
- **целевых позиций и заявок** — портфельного слоя не существует.
