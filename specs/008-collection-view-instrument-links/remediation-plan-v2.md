## 1. Результат, который нужен

Раздел можно принимать, когда сбор обрабатывает всю применимую работу, ошибки и
неизвестные ответы не закрывают полноту, интерфейс и журнал показывают одинаковый итог,
ремонт выполняется одним владельцем и не повторяет готовую работу, а измерения
подтверждают сокращение лишних обращений. Доказанные доступные пропуски восстановлены;
для оставшихся пустот сохранены проверяемые причины либо явно показана неизвестность.

**«100% заполненных ячеек» не является целью.** Законные NULL, отсутствие фьючерса и
подтверждённое отсутствие значения допустимы. Неизвестность готовностью не является.

Три результата фиксируются отдельно: **готовность кода**, **состояние данных**,
**результат приёмки интерфейса**. Зелёный гейт без остальных доказательств не закрывает
раздел. Если внешнее ограничение остаётся, итог называет его и влияние на модель.

## 2. Как выполнять план

1. В одной рабочей сессии выполнять один T215–T233. Не начинать следующий, пока не
   выполнена приёмка текущего. При большой задаче сначала сделать один законченный
   подпункт и оставить точную передачу, а не объявлять весь T выполненным.
2. Прочитать `AGENTS.md`, Constitution, общие правила этого плана, текущий T и относящиеся
   к нему пункты spec/контрактов. Не загружать все старые исследования и все тесты разом.
3. Проверить ветку и рабочее дерево. Использовать текущую ветку исправления либо отдельную
   `fix/*`; не переключать ветку и не уничтожать чужие изменения автоматически.
4. Добавить регрессию наблюдаемого дефекта и исправить его. Единый гейт дорог, поэтому
   `scripts/check.sh --no-docker` запускать после существенного блока связанных кодовых
   задач либо перед рискованным переходом, а не после каждого малого документационного или
   локального шага. Для завершения всей серии в T232 обязателен полный `scripts/check.sh`.
   Частичные pytest/ruff/vitest вместо гейта не запускать. Каждый T по-прежнему получает
   отдельные доказательство, отметку, коммит и push; в записи явно указать, каким ближайшим
   пакетным гейтом он проверен или к какому следующему гейту отложена проверка.
5. Отметку в [tasks.md](./tasks.md) ставить только со ссылкой на доказательство в
   [remediation-results-v2.md](./remediation-results-v2.md). Не переписывать старые тесты
   под неверное поведение ради зелёного результата.
6. Необходимые уточнения требований фиксировать до кода. Если источник не даёт
   доказательства, записать неизвестность; не изобретать семантику ради закрытия задачи.

**Не делать:** новые сервисы/очереди, инженерия признаков, изменения `Daily ML/`,
расчёт полноты в API или frontend, удаление старых наблюдений и журнала, повышение
HTTP-бюджета без команды владельца, автоматический массовый ремонт при миграции/старте.
Не снимать обязательную группу с входа модели для обхода её ошибок.

Документ разрешает подготовку исправлений, но сам не запускает ремонт рабочей БД.
Для T231 нужен конкретный план с диапазоном, источниками и лимитом. Если в текущей
сессии такой объём уже разрешён владельцем, повторное подтверждение не требуется.

## 4. Задания

### T215. Зафиксировать целевые правила до изменения кода

**Файлы:** `spec.md`, `plan.md`, `data-model.md`, `contracts/coverage-api.md`,
`contracts/collection-state-api.md`, `contracts/ui-states.md`; по необходимости
`docs/architecture.md`. Исходные требования — FR-001/005/031/032a-d/033/050/058.

Зафиксировать следующую таблицу; число новых строк не определяет состояние:

| Результат единицы работы | Данные сохраняются | Закрывает работу | Учитывается как недоступность источника |
|---|---|---|---|
| Валидный ответ со значениями, включая законные 0 и NULL | да | в доказанной области | нет |
| Подтверждённое отсутствие/неприменимость с основанием | основание | только указанную область | нет |
| Неизвестный ответ, отсутствующая таблица, чужая дата | ранее полученное | нет | не как транспортный отказ |
| Ошибка транспорта/недоступность сервера | ранее полученное | нет | да, после ограниченных повторов |
| Нарушение контракта ответа | ранее полученное | нет | отдельная причина; допускается прекращение дальнейших бесполезных запросов |
| Остановка/исчерпание бюджета | ранее полученное | нет | нет |

Отдельно определить: итог **плана выбранных источников** и полнота **всей группы** —
разные вопросы. Источник вне выбранного плана не портит итог прогона, но остаётся
неполным в сводке и может блокировать ML. Повтор уже закрытой работы считается
обработанным с сохранением происхождения её доказательства.

Переход: текущая версия 1 уже могла присваиваться ложному успеху (R2), поэтому простое
сохранение доверия всем `coverage_version=1` запрещено. Целевое решение — новая версия
правила с неизменяемой границей старой области; доверие переносится только после
отдельной проверки. Никакого автоматического пересбора прежних окон. Старые справочники
без подтверждения показываются как «нужна проверка», а не как транспортная ошибка.

**Готово:** термин «собрано» имеет проверяемое определение; описаны доказательства,
версия, миграция, исходы сессии и отображение справочника без оси дат. Отмеченные в
старых документах противоречия исправлены; новые требования не выданы за уже работающий код.

### T218. Сохранить доказательства по единицам работы и безопасно сменить версию

**Файлы:** `market_data/{models.py,repository.py,coverage_rule.py}`,

Состав требуемых единиц объявляется источником и его контрактом, а не выводится из
тех строк, которые случайно удалось получить.

1. Добавить компактное хранение проверенного исхода единицы: источник, дата, ключ
   единицы, версия, вид результата, код основания, момент и происхождение проверки.
   Значения остаются в таблицах наблюдений; сырые ответы и секреты в эту таблицу не идут.
2. Подтверждённое отсутствие должно переживать рестарт и исключать повтор этой пары.

3. Новая миграция сохраняет старые данные и исходы, фиксирует границу новой версии один

бумаги, сохранение основания после нового соединения, миграция существующей и пустой БД,
рестарт без сдвига границы и без автодогона старой области.

**Готово:** доказательство конкретной пары можно прочитать после перезапуска;

### T224. Ввести единственного владельца сбора между процессами

**Файлы:** новый небольшой модуль блокировки в `market_data/`, `scheduler.py`,
`runner.py`, `repair_audit.py`, `cli.py`, путь `backfill`; новые PostgreSQL-тесты.

Целевое решение — отдельная **session-level advisory lock PostgreSQL** на сбор рыночных
данных. Выделенное соединение удерживается весь прогон и освобождается в `finally`;
коммиты пачек на рабочем соединении не снимают блокировку. Ключ не общий с брокером/ML.

1. Брать блокировку во внешней точке запуска, до первого внешнего запроса и изменения
   состояния прогона. Охватить ежедневное обновление календаря, ручной сбор, ремонт и
   первичную загрузку. Вложенные функции не захватывают её повторно.
2. Второй исполнитель получает явный конфликт, не ждёт молча и не начинает HTTP.
   Для UI использовать согласованный ответ конфликта; CLI возвращает понятный отказ.
3. Считать старое `running` оборванным только после получения владения. При потере
   соединения владения не продолжать HTTP/запись как будто блокировка ещё удерживается.

**Регрессии двумя независимыми соединениями/процессами:** repair/repair, repair/daily,
repair/manual; промежуточный commit не освобождает владение; исключение освобождает;
процесс завершён → другой может продолжить; живой `running` не переводится в interrupted.

**Готово:** конфликтующий запуск делает 0 внешних попыток. Один `asyncio.Lock` или
только проверка поля `running` приёмкой не являются.
