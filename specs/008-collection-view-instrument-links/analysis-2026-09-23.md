## Найденные дефекты и решения

### A1 · P1 · Текущая версия полноты всё ещё принимает некорректные данные

Места: `market_data/iss/client.py:_validated_block`, `sources/equity_d1.py:rows_to_bars`, `to_decimal`, `sync_equity_daily`; `ingest.py:run_source`.

Валидатор проверяет колонки, длину строк, даты и пагинацию, но не контракт значений идентификатора и числовых полей. Парсер пропускает строку без корректного SECID, а источник назначает успех по наличию исходных строк. Ошибка разбора числа превращается в NULL и также получает доказательство полноты.

Воспроизведено настоящей цепочкой `IssClient → sync_equity_daily → run_source`, с HTTP-подменой и без записи в БД:

| Ответ | Результат текущего кода |
|---|---|
| Одна строка, SECID=NULL, остальные поля и курсор корректны | `ok`, записано 0 строк, `coverage_version=2` |
| SECID=SBER, CLOSE=`broken-value` | `ok`, CLOSE становится NULL, `coverage_version=2` |

**Решение:** проверять идентификаторы и типы/разбор обязательных полей до назначения доказательства. Законный NULL сохранять; ошибку разбора не превращать в законный NULL. Проверка должна охватывать всех потребителей общего преобразования чисел. Повреждённая строка оставляет соответствующую работу незавершённой, полученные корректные данные сохраняются.

### A2 · P1 · Общий запуск нарушает собственное окно позиций

Места: `runner.py:_plan` (около строки 534), `ingest.py:catch_up` / `_catch_up_session` (около строк 714, 810).

План объединяет даты выбранных групп, а исполнитель на каждой дате вызывает все выбранные посессионные источники. Ограничение позиций их собственным окном при исполнении отсутствует. Тест выбора только позиций этого сочетания не проверяет.

На реальном срезе «все группы, всё окно» планирует 313 дат, из которых **232 лежат вне окна позиций**. По текущему алгоритму выбора инструментов на этих датах получается **15 829 потенциальных лишних запросов пар**. Они не выполнялись; это расчёт области работы, без учёта возможных остановок, ошибок и повторов.

Диагностическое воспроизведение: общее окно из пяти дат, окно позиций из двух; на первой дате исполнитель вызывает и котировки, и позиции.

**Решение:** планировать и исполнять конкретные пары «источник — дата» с пересечением выбранного диапазона и собственного окна источника. Даты вне окна не должны попадать ни в HTTP-вызовы, ни в знаменатель успешности выбранной работы. Тот же отбор нужен автоматическому восстановлению и плану ремонта.

### A3 · P1 · Первичная загрузка не является надёжной основой для перезапуска с нуля

Места: `backfill.py:backfill_equity`, `_record_backfill`, `_store_history`; `repository.py:tickers_with_history` (строка 472); `cli.py:_backfill`.

`tickers_with_history()` фактически выбирает все тикеры из `market_asset`. Наличие бумаги в справочнике принимается за завершённую загрузку её истории. После одного ежедневного сбора первичная загрузка может пропустить эту бумагу целиком. Воспроизведение: известный SBER объявлен завершённым, запросов его истории — 0.

Дополнительно, по трассировке кода:

- на пустой базе CLI требует явные тикеры либо предлагает сначала обычный сбор; второй путь приводит к описанному пропуску;
- верхняя дата по умолчанию — `date.today()`, а перед сохранением нет отсечения незакрытой сессии;
- исход первичной загрузки не несёт доказательства покрытия всей доски; последующая проверка будет запрашивать данные снова. Присвоить полноту доски по истории одной бумаги нельзя.

**Решение:** отличать наличие актива от выполненной работы по его историческому диапазону. Завершение и продолжение определять по обработанной области. Верхняя граница — последняя закрытая сессия. Получение состава бумаг должно работать и на пустой базе. По итогам первичного сбора полнота фиксируется тем же правилом, с проверкой всего ожидаемого состава, а не отдельным безусловным успехом.

### A4 · P2 · Частичный диапазон повторно запрашивает уже полученные части

Места: `sources/global_series.py:sync_iss_series_range`, `ingest.py:_catch_up_ranges`, `completeness.py:closed_sessions`; аналогичная организация у ЦБ.

Если один ряд отсутствует на одной дате диапазона, весь источник получает `failed` на весь диапазон. Доказательства успешных частей сохраняются, но следующий вызов загрузчика их не использует. Закрытие требует успешного общего исхода, поэтому доказательства отдельных полных дат также не превращаются в закрытые даты.

Воспроизведение: две даты, пять рядов; у RVI нет второй даты. На первой дате сохранены доказательства всех пяти рядов, на второй — четырёх. Общий исход `failed`; повтор снова делает все пять запросов: суммарно 10 вместо адресного добора остатка.

**Решение:** использовать уже существующие доказательства единиц работы для продолжения. Запрашивать оставшиеся ряды/участки, завершать доказанные даты отдельно. Прерывание диапазонного источника также должно сохранять доказательства полученных частей вместе с данными.

### A5 · P2 · Ежедневный прогон теряет точный итог в журнале

Места: `ingest.py:record_session_outcome` вызывается только внутри ручного `catch_up`; `advance.py` передаёт булев результат; `journal.py:recent_runs` (около строки 333).

Новый успешный ежедневный прогон `ff8e4e11-702c-478e-9ddc-6d26b1c55b6c`, собравший Brent за 21 сентября, в сохранённом журнале имеет:

```json
{"status":"finished","sessions":{"requested":1,"collected":0,"pending":1},"history_limited":true}
```

Точный итог ручного прогона 14 сентября сохранён правильно. Таким образом, исправление общего итога не охватило ежедневный путь. Кроме того, булев результат ежедневного сбора не различает частичный сбор и полный отказ.

**Решение:** одна свёртка результата выбранной работы и одно сохранение итогов для ручного, ежедневного сбора и их продолжения. После рестарта числа должны совпадать с числами в ходе работы. Ограниченный старый журнал не должен быть форматом новых ежедневных прогонов.

### A6 · P2 · Остановка и работающий сбор превращаются в «ошибку источника»

Места: `coverage.py:_source_outcomes` (строка 156), `journal.py:mark_interrupted`, `frontend/.../GroupsSection.tsx:groupBadge` (строка 278).

Сводка объединяет `failed`, `stopped` и `running` в список неудач. Наличие такого элемента даёт источнику `failed`, а группе — «Ошибка источника». После перезапуска незавершённый исход становится `failed` с текстом «прогон прерван». Ошибка нашего обработчика также попадает в общую категорию.

**Решение:** разделить состояние данных, состояние выполнения и причину незавершённости. Остановка, потеря процесса, неизвестный ответ, нарушение контракта и транспортный отказ должны сохраняться и отображаться по своим причинам. Они все могут означать незавершённую работу, но не доказывают отказ внешнего сервиса.

### A7 · P2 · Выбор справочников в ручном сборе не выполняет обещанную работу

Места: `runner.py:_plan`, `plan.py:CATCHUP_PLAN`, `LaunchDrawer.tsx`.

UI позволяет выбрать `reference`, но планировщик учитывает только группы с историей. Выбор одних справочников на реальной базе возвращает `NothingToCatchUpError: пропущенных сессий нет`. При выборе всех групп справочники не входят в план ручного исполнения. В сводке их `scope` из-за поиска в `CATCHUP_PLAN` ошибочно равен `session`.

**Решение:** выбранные справочники обновлять один раз за запуск, независимо от списка исторических дат, с собственным исходом. На уровне отображения корректно использовать суточную область. Это не запрос справочников на каждую сессию.

Дополнительное расхождение: `reference` включён в `daily_ml_required_data_groups`, но `readiness.evaluate` безусловно пропускает группы без окна. Обязательность справочника должна иметь проверяемый смысл; отсутствие оси дат само по себе не означает, что он получен. Проверку необходимости отдельных справочников следует согласовать с контрактом модели, а не ослаблять требования до зелёного результата.

Это локальный замер сети и парсинга с приёмником в памяти, **без стоимости записи в PostgreSQL**. Он не доказывает максимальную скорость или полноту всех исторических дат. Конечные точки сверены с [каталогом ISS](https://iss.moex.com/iss/reference/) и [страницей открытых позиций MOEX](https://www.moex.com/ru/derivatives/open-positions).

Сводка на сохранённой базе: **0,843 / 0,520 / 0,605 с**, по **47 SQL-запросов**. Прежняя тяжёлая обработка журнала действительно ускорена.

Следующие обоснованные оптимизации:

1. Устранить выход позиций за собственное окно — это основной найденный множитель внешних запросов.
2. У котировок `sync_equity_daily` вызывает два отдельных SQL-upsert на каждую бумагу: для 506 строк это уже 1 012 обращений до пакетной записи самих баров. Перевести обновления активов и рядов на пачки; аналогично проверить лоты/ISIN.
3. Продолжать диапазонные источники по остаткам доказанной работы, как описано в A4.
4. `repair_audit.run_plan` исполняет каждый элемент отдельно, поэтому даже диапазонный источник получает однодневные запросы. Объединять совместимые элементы одного источника в точные диапазоны, сохраняя исходный бюджет и область плана.
5. Не считать три немедленных вызова задержанного источника полноценными сетевыми повторами: `PositionsClient` кеширует и `unknown`, а `_run_delayed_source` использует тот же клиент. Повтор ожидания публикации должен иметь осмысленную задержку и возможность получить свежий ответ.

Ускорять позиции без учёта состояния HTML-формы и допустимого темпа нельзя. Первая мера — сокращать ненужную работу, затем измерять оставшуюся.

## Почему два ревью не дали готовой системы

Это вывод по артефактам и коду, а не реконструкция чужих намерений:

- [Ревью 21 сентября](./review-2026-09-21.md) прямо говорило о незавершённости и доказанных пропусках SBER. Они до сих пор не устранены.
- Исправления усилили правило полноты и сняли ложную готовность старых исходов. Разовый переход накопленной базы при этом остался незавершённым.
- В T231 выполнялся ограниченный ремонт четырёх дат Brent, а не восстановление всех групп. Позднее T234 восстановила новую сессию и проверила один ручной запуск котировок/агрегатов. Это полезные результаты, но они не доказывают готовность всей истории.
- Проверка только позиций не обнаружила нарушение их окна при выборе всех групп. Проверка ручного результата не обнаружила отсутствие сохранённого результата ежедневного сбора. Проверка формы JSON не обнаружила ошибочные типы значений.
- Отметки завершения исправлений и успешный общий гейт использовались шире, чем позволяют их фактические доказательства. Незавершённая приёмка данных оставалась в примечаниях.

## Предлагаемое исправление

1. Исправить A1–A3 до массовой перепроверки: корректность доказательства, точную область работы и первичную загрузку. Использовать существующие компоненты и таблицу доказательств; новые сервисы не нужны.
2. Завершить продолжение частичных диапазонов, сохранение ежедневных итогов, причины остановки и ручное обновление справочников. Единица плана — применимая работа конкретного источника, а не общая дата для всех.
3. Выполнить один управляемый проход по текущим окнам групп. Старые исходы без доказательств нельзя объявить полными по числу строк: для значительной части истории понадобится повторная проверка источника. Полученные значения сохранять и адресно обновлять; исправные доказанные единицы пропускать. Для неизвестных ответов позиций искать проверяемое основание отсутствия/неприменимости; первая найденная дата наблюдения таким основанием не является.
4. Сохранить существующие данные. Удалять или адресно заменять только записи, для которых доказана ошибочность, с сохранением происхождения исправления. Очередную глобальную смену версии, заново обнуляющую доверие ко всем группам, не использовать как замену анализу затронутых данных.
5. Упростить основной экран по замечаниям владельца. Убрать повторяющиеся счётчики и объяснения про версии/прежние отчёты. Дата данных и момент обновления состояния имеют разные значения. Техническую причину оставлять в деталях конкретной незавершённой работы. Состояние истории не должно изображать текущую недоступность источника.

Приёмка должна показать один полный жизненный цикл на изолированной базе: загрузка с нуля; повтор без лишних запросов; новая закрытая сессия; законные NULL и подтверждённая неприменимость; испорченный ответ; остановка в середине источника; продолжение; перезапуск процесса; совпадение сводки, журнала, планируемого остатка и готовности ML. Отдельно — выбор всех групп при разных размерах окон, чтобы число запросов позиций вне своего окна было ровно нулём.

Готовность всей истории подтверждается только после адресного восстановления и аудита фактического результата. Доступность внешнего источника нельзя гарантировать, но система обязана получить всё доступное в нужной области, сохранить прогресс и точно назвать неподтверждённый остаток.
