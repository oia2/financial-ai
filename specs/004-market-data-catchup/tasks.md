## Dependencies

**Порядок фаз**:

```text
Phase 1 (Setup) → Phase 2 (Foundational) → Phase 3 (US1) → Phase 4 (US2) → Phase 5 (US3) → Phase 6 (Polish)
```

**Блокирующие связи**:

- T003 → T004 → T005: миграция, модель, запись — один и тот же признак прогона;
- T006 → T007: модуль обнаружения опирается на запрос к хранилищу;
- T007 → T017, T030, T033, T040: перечень пропусков нужен догону, команде просмотра,
  объявлению полноты и разграничению с первичной загрузкой;
- T017 → T018: догон должен существовать, прежде чем встраиваться в порядок шагов;
- T033 → T034: объявление сначала попадает в манифест, потом в запрос;
- T034 → T035 → T036: код, эмулятор, контракт — в этом порядке, иначе документ описывает
  несуществующее;
- T036 → T037: отметка в спецификации 003 ссылается на исправленный контракт.

**Независимость историй**: US1 закрывает дыру, US2 делает её видимой, US3 разграничивает с
первичной загрузкой. US2 и US3 не требуют завершения US1: перечень пропусков и сообщение о
первичной загрузке осмысленны и без догона.

## Implementation Strategy

**MVP** — Phase 1 + Phase 2 + Phase 3 (US1). Дыра начинает закрываться сама, а это главное:
без этого простой любой длины оставляет постоянный дефект в данных.

**Порядок дальше** соответствует срезам плана:

1. **Срез A** — Phase 2 плюс T030, T032 из Phase 4: видно, чего не хватает. Полезно даже
   без догона, потому что сегодня дыру нельзя обнаружить иначе как случайно;
2. **Срез B** — Phase 3: дыра закрывается;
3. **Срез C** — остальное из Phase 4: остаточная неполнота объявлена модели.

**Почему объявление полноты идёт последним**: оно расширяет контракт, зафиксированный
фичей 003, и требует согласованной правки кода, эмулятора и двух документов. Делать это
раньше, чем догон закрывает дыру, значит сначала описать неполноту, а потом научиться её
устранять.
