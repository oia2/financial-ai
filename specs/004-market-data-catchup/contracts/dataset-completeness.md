# Contract: объявление полноты окна в запросе ранжирования

Расширение контракта
[`specs/003-moex-data-ingestion/contracts/daily-ml-request.md`](../../003-moex-data-ingestion/contracts/daily-ml-request.md).
Базовый контракт действует целиком; здесь описано **только добавленное**.

## Зачем

Модель не может определить, что часть окна не собрана. В рядах пропуск выглядит одинаково
в трёх разных случаях:

| Что произошло | Как выглядит в наборе |
|---|---|
| Сессии не было | сессии нет на оси |
| Сессия была, бумага не торговалась | `null` |
| Сессия была, за ней не ходили | `null` |

Второй и третий неразличимы, а последствия у них разные: в одном случае это факт рынка, в
другом — след простоя платформы. Знание есть только у отправителя, поэтому объявляет он.

Без объявления неполнота приезжает к модели молча, актив выпадает из ранжирования по маске
и в ответе выглядит исключённым **по решению модели**. Ровно этот дефект фича и устраняет.

## Добавляется в тело запроса

```json
{
  "asof_date": "2026-08-28",
  "dataset": {
    "ref": "file:///datasets/20260828T183000Z-3aab1480aa97",
    "digest": "sha256:9f2c…",
    "windows": {
      "price_sessions": 314,
      "aggregate_sessions": 314,
      "global_sessions": 314,
      "positions_sessions": 82
    },
    "incomplete": [
      { "session_date": "2026-08-14", "sources": ["equity_d1", "equity_agg"] },
      { "session_date": "2026-08-15", "sources": ["futures_positions"] }
    ]
  },
  "assets": [
    { "asset_id": "EQ_AST_SBER", "price_series_id": "EQ_PRS_SBER" }
  ]
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `dataset.incomplete` | array | Сессии окна, данные за которые неполны. **Присутствует всегда** |
| `dataset.incomplete[].session_date` | date `YYYY-MM-DD` | Торговая сессия окна |
| `dataset.incomplete[].sources` | array of string | Источники, оставшиеся незакрытыми за эту сессию |

## Инварианты

- **Поле присутствует всегда.** Пустой массив — значимое утверждение «окно полно».
  Отсутствие поля и пустой массив различаются: первое означало бы, что отправитель о
  полноте не высказался.
- **Даты принадлежат окну** и являются торговыми сессиями календаря. Неторговый день в
  перечень не попадает: пропуска там нет.
- **Перечень отсортирован** по дате по возрастанию — чтобы одинаковое содержимое давало
  одинаковый дайджест.
- **Объявление входит в дайджест набора.** Два набора с одинаковыми рядами и разной
  полнотой окна обязаны иметь **разные** дайджесты: иначе различие можно скрыть, а на
  дайджесте держится сопоставимость пары «запрос — ответ» постфактум.
- **Тот же перечень лежит в манифесте набора** по ссылке `dataset.ref`. Запрос и манифест
  не расходятся.

## Что не меняется

- состав семейств данных, их окна и раскладка — как зафиксировано фичей 003;
- форма ответа: признак неполноты в ответе **не появляется**. Отличить исключение по
  решению модели от последствия несобранной сессии позволяет пара «ответ + сопровождающий
  его вход»;
- поведение при неполном окне: ранжирование **выполняется**. Отказ означал бы, что одна
  сессия, которую биржа уже никогда не отдаст, останавливает систему навсегда.

## Ошибки

Коды базового контракта действуют без изменений. Добавляется одна ситуация:

| Код | Ситуация | `detail.code` |
|---|---|---|
| `422` | `dataset.incomplete` отсутствует, либо элемент не содержит `session_date` или `sources` | `invalid_request` |

## Эмулятор

Эмулятор принимает поле и проверяет его форму наравне с остальным запросом. В вычислениях
не использует — как не использует и сами ряды: он по-прежнему изображает скоры, а не
считает их. Признак `emulated: true` в ответе сохраняется.

Отдельного кода ошибки для несогласованности перечня с содержимым набора у эмулятора нет:
набор он не читает. Такая проверка относится к настоящей модели — как `dataset_digest_mismatch`
и `dataset_not_found` в базовом контракте.
