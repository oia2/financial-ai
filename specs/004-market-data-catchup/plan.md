# Implementation Plan: Догон пропущенных торговых сессий

**Branch**: `feature/market-data-catchup` | **Date**: 2026-09-03 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/004-market-data-catchup/spec.md`

## Summary

Ежедневный цикл собирает одну сессию и не знает о пропусках. Фича добавляет три вещи:
**обнаружение** дыры сравнением календаря с наблюдениями, **догон** пропущенных сессий в
пределах окна набора и **объявление полноты окна**, которое едет к модели вместе с
набором.

Новых сервисов, таблиц и контейнеров не появляется. Обнаружение — запрос к существующим
таблицам, догон — повторное применение уже написанного сбора к другой дате, объявление
полноты — поле в манифесте набора и в запросе ранжирования.

## Technical Context

**Language/Version**: Python 3.12

**Primary Dependencies**: SQLAlchemy 2.0 (async), asyncpg, httpx, Alembic, FastAPI, `uv`

**Storage**: PostgreSQL 17 — существующие таблицы `market_*`; одна новая колонка

**Testing**: pytest, тесты на подделках источников; тесты БД помечены `pytest.mark.db`

**Target Platform**: Linux-контейнеры, Docker Compose; сбор выполняет `backend-worker`

**Project Type**: web-service — backend (api + worker из одного пакета) и отдельный
контейнер эмулятора звена ранжирования

**Performance Goals**: догон месяца простоя (~21 сессия) — порядка 100 обращений к
источникам; догон полного окна (314 сессий) — порядка 1500 обращений, разово при старте.
Для источников с выборкой за период число обращений от длины дыры не зависит

**Constraints**: общий HTTP-слой ISS — 6 повторов, таймаут 60 с; передатирование
запрещено; `float` на пути «биржа → БД → запрос» запрещён; догон не должен задерживать
сбор текущей сессии

**Scale/Scope**: около 288 активов, окно 314 торговых сессий, двенадцать источников

**Structure Decision**: код остаётся внутри существующего пакета `backend/`. Новый модуль
один — `market_data/gaps.py`, потому что «что пропущено» — самостоятельное знание, которое
нужно и догону, и объявлению полноты, и команде просмотра. Всё остальное — дополнения к
уже существующим модулям: догон не вводит нового способа собирать данные, он применяет
существующий к другим датам.

Отдельный контейнер или процесс не заводится: по канонической диаграмме в MOEX ходит
`backend-worker`, и догон — часть его работы, а не новая роль.

## Порядок работ: три среза

| Срез | Содержание | Проверяемый результат |
|---|---|---|
| **A** | обнаружение пропусков, команда просмотра, признак прогона | Видно, каких сессий не хватает, без чтения логов |
| **B** | догон в цикле: порядок шагов, инкрементальность, прерываемость, разграничение с первичной загрузкой | Дыра закрывается сама |
| **C** | объявление полноты окна: манифест, дайджест, запрос, эмулятор, контракт | Неполнота входа отличима от решения модели |

Срез A самодостаточен и полезен сам по себе: он превращает молчаливую дыру в видимую,
даже если догон ещё не написан. B закрывает дыру. C делает остаточную неполноту честной.
