# Implementation Plan: Эмулятор Daily ML

**Branch**: `feature/daily-ml-emulator` | **Date**: 2026-08-29 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-daily-ml-emulator/spec.md`

## Summary

Отдельный контейнер, который изображает работу звена ранжирования активов: принимает дату
решения и возвращает упорядоченный список активов со скорами в той форме, которую потом
вернёт настоящая модель. Содержательных вычислений нет — порядок задаётся тривиальным
детерминированным правилом от даты (циклический сдвиг настроенной вселенной), скор
выводится из ранга по фиксированной убывающей лестнице.

Технический подход: тот же стек, что уже используется в проекте (Python 3.12 + FastAPI +
uv), но **отдельный** uv-проект в собственной директории `daily-ml-emulator/`, без
зависимостей от пакета `financial_ai`, без БД и без секретов. FastAPI выбран в том числе
потому, что закрывает FR-022 «схема эндпоинтов от самого сервиса» без единой строки кода.

Форма ответа перенесена из исследовательского репозитория `MR-MASTER-DRO`, а не придумана:
ключ `decision_date + asset_id`, идентичность актива `asset_id` + `price_series_id`,
кросс-секционный ранжирующий скор внутри даты.

## Technical Context

**Language/Version**: Python 3.12 (совпадает с `backend/`, `requires-python = ">=3.12"`)

**Primary Dependencies**: FastAPI (HTTP + автоматическая OpenAPI-схема и страница
документации), uvicorn (ASGI-сервер), pydantic v2 (схемы ответа), pydantic-settings
(конфигурация из переменных окружения). Стандартной библиотеки хватает на всё остальное:
`datetime`, `decimal`, `json`.

**Storage**: N/A — эмулятор без состояния (FR-012). Вселенная активов читается из
JSON-файла при старте, в память; ничего не пишется.

**Testing**: pytest + `fastapi.testclient` (внутри — httpx). Асинхронности в эмуляторе нет,
`pytest-asyncio` не нужен.

**Target Platform**: Linux-контейнер, `python:3.12-slim-bookworm` — тот же базовый образ,
что у `backend/`

**Project Type**: Изолированный HTTP-сервис в одном контейнере (не web-приложение, не
библиотека). Собственный uv-проект, не подпроект `backend/`.

**Performance Goals**: ответ < 1 с при вселенной до 200 активов (SC-002). Фактически
ранжирование — один проход по списку в памяти; порядок величины — единицы миллисекунд.

**Constraints**: без секретов, без БД, без сети наружу (FR-018, SC-006); детерминизм
между запросами и перезапусками (FR-009); скоры в ответе — строки (FR-007); никакой
логики настоящей модели (FR-011).

**Scale/Scope**: один эндпоинт ранжирования + health, вселенная по умолчанию — 10 активов,
ограничение сверху — 200 (граница из SC-002). Оценка объёма: ~250 строк кода и ~250 строк
тестов.

**Дополнение к структуре, внесённое после первичного плана.** По запросу владельца
проекта в репозитории появился каталог `docs/`, а каталог `source/` удалён:

- `docs/container-diagram.svg` — каноническая диаграмма контейнеров, перенесена из
  `source/Диаграмма конейнеров FinA.svg` через `git mv` (история сохранена). Имя
  приведено к латинице: в прежнем была опечатка, а кириллица в путях создаёт проблемы
  с кодировкой на Windows;
- `docs/architecture.md` — описание системы. Раздел «Архитектура проекта» в `AGENTS.md`
  пересказывал состав компонентов и потоки данных; теперь он ссылается сюда, а таблица
  отступлений развёртывания живёт в одном месте;
- `docs/daily-ml-model.md` — описание модели ранжирования: целевая переменная, вход,
  выход, состояние. Документ переживёт эмулятор, поэтому не может лежать ни в
  `daily-ml-emulator/`, ни в `specs/002-*/`.

Эта работа выходит за объём фичи (её нет ни в требованиях, ни в задачах T001–T040) и
зафиксирована здесь для прослеживаемости, как того требуют Принципы III и V.

**Structure Decision**: отдельная директория верхнего уровня `daily-ml-emulator/` с
собственным uv-проектом. Она повторяет уже сложившуюся в репозитории схему — `backend/` и
`frontend/` тоже лежат в корне, каждый со своим менеджером пакетов и своим Dockerfile
рядом с кодом, а всё, что относится к развёртыванию, живёт в `deployments/`.

Эмулятор **не** размещается внутри `backend/`: он не является частью пакета
`financial_ai`, не разделяет с ним ни зависимости (SQLAlchemy, asyncpg, SDK T-Bank), ни
конфигурацию, ни жизненный цикл, и должен быть удаляем одной директорией в момент, когда
появится настоящая модель.
