# Contract: Daily ML Emulator (HTTP API)

**База**: `http://daily-ml-emulator:8000` внутри сети docker compose,
`http://localhost:${DAILY_ML_EMULATOR_PORT:-8100}` снаружи

**Аутентификация**: нет. Эмулятору не нужны ни секреты, ни токены (FR-018)

> **Это эмулятор.** Все скоры вымышлены и получены циклическим сдвигом настроенного
> списка активов. Никакой модели, никаких рыночных данных, никаких вычислений за ними нет.
> Каждый успешный ответ содержит `"emulated": true` — потребитель обязан это проверять,
> пока звено ранжирования не заменено настоящей моделью.

Схему этих же эндпоинтов отдаёт сам запущенный сервис: `/openapi.json` — машиночитаемо,
`/docs` — страницей (FR-022).

---

## `GET /rankings`

Возвращает ранжирование всей вселенной активов на указанную дату решения.

Вселенной владеет эмулятор — вызывающая сторона её не передаёт и повлиять на состав не
может (FR-002). Так же устроена и настоящая модель: она определяет вселенную сама.

### Параметры запроса

| Параметр | Тип | Обяз. | Смысл |
|---|---|---|---|
| `decision_date` | string `YYYY-MM-DD` | да | Дата решения, на которую нужно ранжирование |

Торговый календарь MOEX эмулятору неизвестен: он отвечает на любую синтаксически
корректную дату, включая выходные и даты в будущем. Проверка торгового дня — обязанность
настоящей модели.

### `200 OK`

```json
{
  "decision_date": "2026-08-28",
  "model_id": "daily-ml-emulator-v1",
  "generated_at": "2026-08-29T09:14:02Z",
  "emulated": true,
  "emulation_notice": "Значения вымышлены эмулятором Daily ML. Модели, рыночных данных и вычислений за ними нет.",
  "items": [
    { "rank": 1, "asset_id": "EQ_AST_ROSN", "price_series_id": "EQ_PRS_ROSN", "score": "0.9091" },
    { "rank": 2, "asset_id": "EQ_AST_NVTK", "price_series_id": "EQ_PRS_NVTK", "score": "0.8182" },
    { "rank": 3, "asset_id": "EQ_AST_TATN", "price_series_id": "EQ_PRS_TATN", "score": "0.7273" }
  ]
}
```

Пример сокращён до трёх позиций; в действительности `items` содержит всю вселенную —
10 позиций при конфигурации по умолчанию.

| Поле | Тип | Смысл |
|---|---|---|
| `decision_date` | string | Дата решения из запроса, повторённая в ответе |
| `model_id` | string | Идентификатор модели, выдавшей ранжирование |
| `generated_at` | string, UTC ISO-8601 | Момент формирования ответа |
| `emulated` | boolean | Всегда `true`. Машиночитаемый признак эмуляции (FR-006) |
| `emulation_notice` | string | Человекочитаемое предупреждение |
| `items` | array | Позиции ранжирования, упорядоченные по возрастанию `rank` |
| `items[].rank` | integer | Место в порядке убывания скора; `1` — лучший |
| `items[].asset_id` | string | Экономический актив, устойчивый к переименованиям тикера |
| `items[].price_series_id` | string | Сшиваемый ценовой ряд этого актива |
| `items[].score` | string | Кросс-секционный ранжирующий скор внутри даты решения |

### Инварианты ответа

1. `items` содержит всю вселенную: ровно N позиций, без добавленных и без пропущенных.
2. `rank` пробегает непрерывный ряд `1..N` без повторов; `items` отсортирован по нему.
3. `asset_id` уникален в пределах ответа — пара `decision_date + asset_id` остаётся ключом,
   как в score-поверхности `MR-MASTER-DRO`.
4. `score` строго убывает по мере роста `rank`.
5. `score` — **строка**, а не число. Так же в этом проекте передаются денежные величины:
   значение, полученное потребителем, точно совпадает с выданным.
6. Один и тот же `decision_date` всегда даёт один и тот же состав `items` — в том числе
   после перезапуска контейнера. Между запросами меняется только `generated_at`.
7. Разные даты решения дают разный порядок активов.

### Смысл `score`

Осмыслен **только порядок внутри одной даты решения**. Абсолютное значение интерпретации
не имеет, сравнению между датами не подлежит и доходности не означает. Это свойство
настоящей модели, обучаемой pairwise ranking objective, а не упрощение эмулятора.

### `422 Unprocessable Entity`

Параметр `decision_date` отсутствует или не разбирается как дата `YYYY-MM-DD`:

```json
{
  "detail": {
    "code": "invalid_decision_date",
    "message": "decision_date должен быть датой в формате YYYY-MM-DD"
  }
}
```

Ранжирование при этом не выдаётся (FR-013). Форма ошибки — та же, что у остальных
сервисов проекта: `{"detail": {"code": "...", ...}}`.

---

## Прочие ошибки

Обращения, не попавшие ни в один эндпоинт, обрабатываются тем же обработчиком и
возвращаются в той же форме — потребителю не нужно разбирать два разных формата ошибок.

| Ситуация | Код | Тело |
|---|---|---|
| Неизвестный путь | `404` | `{"detail": {"code": "error", "message": "Not Found"}}` |
| Неподдерживаемый метод (например, `POST /rankings`) | `405` | `{"detail": {"code": "error", "message": "Method Not Allowed"}}` |

Код `error` — общий: он означает «ошибка обращения», а не конкретную причину, и по нему
не следует ветвить логику. Осмысленные машиночитаемые коды имеют только ошибки уровня
запроса, как `invalid_decision_date` выше.

Полный перечень кодов, которые возвращает эмулятор: `200`, `404`, `405`, `422`.

## `GET /health`

Готовность принимать запросы (FR-015). Используется healthcheck'ом docker compose.

### `200 OK`

```json
{ "status": "ok" }
```

Ответ `200` означает, что конфигурация вселенной уже загружена и прошла валидацию:
непригодная конфигурация не даёт контейнеру подняться (см. ниже), поэтому «здоровый, но
неработоспособный» эмулятор невозможен.

---

## `GET /openapi.json` и `GET /docs`

Машиночитаемая схема эндпоинтов и страница документации, отдаваемые самим сервисом
(FR-022). Работают без конфигурации, ровно как `/api/docs` у `backend-api` и
`/internal/docs` у `backend-worker`.

---

## Поведение при непригодной конфигурации

Пустая вселенная, дубликаты `asset_id` или `price_series_id`, пустые значения полей,
нечитаемый JSON, более 200 активов — **отказ старта**: процесс завершается с ненулевым
кодом и сообщением, называющим причину и конкретную запись (FR-017).

Это сознательно не ошибка уровня запроса. Контейнер, поднявшийся со сломанной
конфигурацией и отвечающий `500` на каждое обращение, обнаружил бы неисправность позже и
дальше от причины.

## Что переживёт замену эмулятора настоящей моделью

Разделение обязательно (FR-023): портфельный слой должен видеть, на что можно опираться.

| Поле | Судьба | Основание |
|---|---|---|
| `decision_date` | **остаётся** | Ключ выдачи в `MR-MASTER-DRO` |
| `items[].asset_id` | **остаётся** | Канонический идентификатор актива, `docs/specs/entity_identity.md` |
| `items[].price_series_id` | **остаётся** | Требуется для непрерывности ценового ряда, там же |
| `items[].score` | **остаётся** | Кросс-секционный ранжирующий скор |
| `items[].rank` | **остаётся** | Производное от `score`, порядок внутри даты |
| `model_id`, `generated_at` | **остаются** | Общие для любой выдачи ранжирования |
| `emulated`, `emulation_notice` | **исчезнут** | Существуют только у эмулятора |

Потребителю: закладываться на **наличие** `emulated` в будущем не нужно, но **проверять**
его, пока он есть, обязательно — иначе вымышленные скоры однажды попадут в решение о
сделке как настоящие.

`fold_id` и `split_role`, входящие в ключ score-поверхности исследовательского
репозитория, в контракт не перенесены: они описывают walk-forward эксперимент, а не
промышленную выдачу.

**Не покрыто этой фичей** и потребуется при подключении портфельного слоя: отображение
`asset_id` на FIGI/UID T-Bank и торговый календарь MOEX.
