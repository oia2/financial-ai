# Research: Эмулятор Daily ML

Проверенные факты и принятые решения. Документ отвечает на вопрос «почему так», чтобы
следующий участник работы не переоткрывал те же альтернативы.

Источники истины: исследовательский репозиторий `MR-MASTER-DRO` (подключён локально как
`Daily ML/`, в Git этого проекта не входит), существующий код платформы,
`.specify/memory/constitution.md`.

---

## 1. Стек эмулятора

**Решение**: Python 3.12 + FastAPI + uvicorn + pydantic v2 + pydantic-settings, отдельный
uv-проект, pytest для тестов, ruff и mypy для проверок.

**Обоснование**:

- Стек уже используется в `backend/` — в проекте не появляется ни одного нового языка,
  менеджера пакетов или набора линтеров. Это прямое следствие Принципа II: проверки,
  Dockerfile и привычки переиспользуются, а не изобретаются.
- FastAPI закрывает FR-022 «эмулятор сам отдаёт машиночитаемую схему и страницу
  документации» без единой строки кода: `/openapi.json` и `/docs` появляются сами. Оба
  существующих сервиса проекта уже так и работают (`backend/src/financial_ai/api/app.py:33`,
  `backend/src/financial_ai/worker/app.py:49`).
- Настоящая модель написана на Python (PyTorch): когда эмулятор будет заменён, граница
  останется в том же языке.

**Альтернативы отвергнуты**:

- **Go / Node** — меньший образ, но новый toolchain в `scripts/check.sh` и вторая
  экосистема зависимостей ради заглушки на ~250 строк.
- **Голый `http.server` без фреймворка** — «ещё проще», но тогда схему эндпоинтов и
  валидацию даты пришлось бы писать руками, а FR-022 требует машиночитаемую схему. Это
  экономия одной зависимости ценой собственного кода — то есть не упрощение.
- **Подпроект внутри `backend/`** — эмулятор притащил бы SQLAlchemy, asyncpg и SDK T-Bank,
  которые ему не нужны и которых по FR-018 у него быть не должно.

## 2. Правило ранжирования: как изображать работу модели без вычислений

**Решение**: циклический сдвиг настроенной вселенной, величина сдвига — от даты решения.

```text
N      = число активов во вселенной
offset = порядковый номер даты (date.toordinal()) mod N
rank(i) = ((i + offset) mod N) + 1        # i — позиция актива в конфигурации
score(rank) = 1 - rank / (N + 1)          # Decimal, 4 знака, строкой
```

**Обоснование**:

- Удовлетворяет FR-010 (разные даты — разный порядок) и FR-009 (одна дата — всегда тот же
  ответ, в том числе после перезапуска) одновременно, потому что зависит только от даты и
  конфигурации, а не от времени запроса, состояния процесса или генератора случайных чисел.
- Никаких рыночных данных, признаков, весов и окон — FR-011 соблюдён буквально.
- Скоры различны по построению, поэтому ранги однозначны, а ничьих не возникает. Сортировка
  всё равно делается с вторичным ключом `asset_id` — так порядок не зависит от порядка
  обхода структуры данных даже при изменении правила.
- Правило объясняется одной формулой, и его легко проверить тестом.

**Альтернативы отвергнуты**:

- **Псевдослучайная перестановка с сидом от даты** (`random.Random(date).shuffle`) — выглядит
  реалистичнее, но детерминизм тогда опирается на стабильность реализации генератора между
  версиями Python. Для требования «тот же ответ после перезапуска» это лишний риск ради
  косметики.
- **Фиксированный порядок для всех дат** — отвергнут владельцем проекта: портфельный слой
  никогда не увидел бы ротацию состава и не смог бы проверить ребалансировку.
- **Случайное значение на каждый запрос** — отменяет FR-009 и делает тесты потребителя
  нестабильными.

## 3. Форма ответа: что перенесено из исследовательского репозитория

**Решение**: ключ `decision_date + asset_id`; идентичность актива — `asset_id` +
`price_series_id`; `score` как кросс-секционный ранжирующий скор внутри даты; `fold_id` и
`split_role` не переносятся.

**Обоснование** — всё проверено по коду и спецификациям `MR-MASTER-DRO`:

| Факт | Где зафиксировано |
|---|---|
| Ключ строк score-поверхности — `fold_id + split_role + decision_date + asset_id` | `pipelines/signal_layer_pre_ig/anchor_score_surface_exporter.py:42`, `docs/specs/v7_regime_gate_v1.md` |
| `fold_id` и `split_role` относятся к walk-forward эксперименту, а не к выдаче | `configs/data_plane/model_input_v1_contract.json` (`split_roles: train/validation/test`) |
| При склейке по дате и активу ключом становится ровно `decision_date + asset_id` | `anchor_score_surface_exporter.py:43` (`DATE_ASSET_KEYS`), `drop_duplicates` по нему |
| Тикер — маршрутный ключ сырых файлов, а не идентификатор сущности | `docs/specs/entity_identity.md`, раздел Core Rule |
| Канонические идентификаторы — `asset_id` (экономический актив) и `price_series_id` (сшиваемый ценовой ряд) | `docs/specs/entity_identity.md:21-24` |
| Один `asset_id` может содержать несколько `price_series_id` | `docs/specs/entity_identity.md:130` |
| Значим порядок внутри даты, а не абсолютное значение скора | pairwise ranking objective, `docs/specs/pre_ig_signal_extractor_v1.md` |

Про последнюю строку таблицы важно: раз один `asset_id` способен нести несколько
`price_series_id`, уникальность `decision_date + asset_id` (FR-008) не следует из
идентичности автоматически — её обеспечивает сама модель, выбирая удерживаемый ряд.
Именно так устроен экспортёр score-поверхности. Эмулятор повторяет это соглашение: в
конфигурации вселенной у одного `asset_id` ровно один `price_series_id`, и это
проверяется при старте.

## 4. Формат значений идентификаторов во вселенной по умолчанию

**Решение**: `EQ_AST_<ТИКЕР>` и `EQ_PRS_<ТИКЕР>` — например, `EQ_AST_SBER` и `EQ_PRS_SBER`.

**Обоснование**: форма взята из кода построения идентификаторов
(`pipelines/data_plane_step0/pipeline.py:901-927`): якорем служит предпочтительный ISIN,
**а при его отсутствии — тикер**, после чего добавляется префикс `EQ_AST_` или `EQ_PRS_`.
То есть тикерный якорь — законный вариант формата, а не выдумка.

Сознательно **не** используются настоящие ISIN: подставить в фикстуру эмулятора ISIN,
который выглядит как настоящий, но не проверен по реестру, — значит внести в репозиторий
правдоподобные, но недостоверные данные. Тикерный якорь читается человеком (`EQ_AST_SBER`)
и очевидно синтетичен.

**Альтернатива отвергнута**: вселенная из голых тикеров (`SBER`) — нарушает
`entity_identity.md` и приучает потребителя к идентификатору, которого в контракте модели нет.

## 5. Числовые значения в JSON

**Решение**: `score` передаётся строкой; внутри считается `Decimal`, квантуется до 4 знаков.

**Обоснование**: это то же правило, по которому в проекте передаются денежные величины
(`Decimal` в домене, строки в JSON) — оно существует, чтобы значение, полученное
потребителем, точно совпадало с выданным, без сюрпризов двоичной плавающей точки. FR-007
распространяет его на скор. Заодно это делает проверку SC-003 («100 идентичных ответов»)
буквальной: строки сравниваются посимвольно.

`rank` остаётся целым числом: это порядковый номер, а не измеряемая величина.

## 6. Место в развёртывании: отдельный сервис в существующем compose

**Решение**: добавить сервис `daily-ml-emulator` в
`deployments/docker-compose/docker-compose.yml` — без `depends_on`, без переменных других
сервисов, без общей БД, с собственным портом.

**Обоснование**:

- Владелец проекта сформулировал цель прямо: «чтобы можно было поднимать систему с
  эмулятором». Отдельный compose-файл этой цели не достигает — стенд перестал бы
  подниматься одной командой.
- Появление сервиса в compose **не является** подключением к системе: ни один компонент к
  эмулятору не обращается, эмулятор не обращается ни к кому. Раздел «Вне объёма»
  спецификации запрещает связывать эмулятор с `backend-api`, `backend-worker`, PostgreSQL и
  frontend — этот запрет соблюдается.
- Побочно закрывается SC-007: `scripts/check.sh` выполняет `docker compose build`, который
  собирает все сервисы файла, поэтому сборка образа эмулятора попадает в гейт сама.

**Альтернатива отвергнута**: отдельный `docker-compose.emulator.yml` — потребовал бы второй
команды запуска и второго шага сборки в `check.sh`, не давая взамен ничего: изоляция и так
обеспечена отсутствием связей.

## 7. Конфигурация вселенной без пересборки образа

**Решение**: JSON-файл, путь к нему — в `DAILY_ML_EMULATOR_UNIVERSE_PATH`. Файл по
умолчанию (`universe/default.json`) запечён в образ; другой подставляется монтированием
тома.

**Обоснование**: в проекте уже есть ровно этот приём — `nginx.conf` монтируется в контейнер
`frontend`, поэтому правится без пересборки. Список из 200 активов в переменной окружения
нечитаем и неудобен в правке; файл диффается и ревьюится.

**Альтернатива отвергнута**: вселенная в переменной окружения как inline-JSON — работает
для трёх активов и разваливается на двухстах.

## 8. Коды и форма ошибок

**Решение**: `{"detail": {"code": "..."}}`, `422` для нераспознаваемой даты решения.

**Обоснование**: единая форма ошибок уже зафиксирована контрактом первой фичи
(`specs/001-investment-account-state/contracts/backend-api.md`, пункт 5 раздела инвариантов:
«Ошибки отдаются в едином виде: `{"detail": {"code": "...", ...}}`»), и там же `422`
используется для значения, не прошедшего валидацию. Эмулятор не вводит второго соглашения.

Непригодная конфигурация (пустая вселенная, дубликаты `asset_id`) — не ошибка запроса, а
отказ старта: контейнер завершается с ненулевым кодом и внятным сообщением (FR-017).
Отвечать `500` на каждый запрос при заведомо сломанной конфигурации хуже — неисправность
обнаружится позже и дальше от причины.

## 9. Метод HTTP для запроса ранжирования

**Решение**: `GET /rankings?decision_date=YYYY-MM-DD`.

**Обоснование**: запрос ничего не меняет и не создаёт — эмулятор без состояния (FR-012), а
ответ полностью определяется датой (FR-009). Это ровно семантика `GET`: идемпотентно,
кэшируемо, проверяется одним `curl` без тела запроса, что делает инструкцию из FR-020
короче.

**Альтернатива отвергнута**: `POST /rankings` с телом — понадобился бы, если бы вселенная
приходила от вызывающей стороны, но владелец проекта решил обратное: вселенной владеет
эмулятор.
