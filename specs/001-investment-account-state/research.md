## 1. Python SDK для T-Invest API

### Decision

Использовать `t-tech-investments`, устанавливая его **из GitLab-реестра T-Bank**, а не из
публичного PyPI:

```text
pip install t-tech-investments==1.49.3 \
  --extra-index-url https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple
```

Импорт: `from t_tech.invest import Client, AsyncClient`.

### Rationale (проверено 2026-08-26)

| Проверка | Результат |
|---|---|
| `https://pypi.org/simple/t-tech-investments/` (JSON API) | `{"files": [], "project-status": {"status": "quarantined"}, "versions": []}` |
| `https://pypi.org/pypi/t-tech-investments/json` | HTTP 404 |
| `https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple/t-tech-investments` | HTTP 200, версии от 1.0.0 до **1.49.3**, `data-requires-python=">=3.8"` |
| Установочная команда в документации T-Bank | `pip install t-tech-investments --index-url https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple` |

То есть **имя пакета в исходном плане верное, но `pip install t-tech-investments` из
публичного PyPI не сработает**: проект там на карантине и не содержит ни одного файла.
Это прямое требование к сборке backend-образа и к CI — дополнительный индекс обязателен.

Из README библиотеки:

- поддерживаются **синхронный и асинхронный gRPC-клиенты** (`Client` / `AsyncClient`);
- переключение боевого контура и песочницы через `target`: `INVEST_GRPC_API` /
  `INVEST_GRPC_API_SANDBOX` (`t_tech.invest.constants`);
- при ошибке валидации TLS предусмотрена переменная `SSL_TBANK_VERIFY=True`, включающая
  поставляемый с библиотекой сертификат МинЦифры.

### Уточнение формулировки

README библиотеки содержит явный дисклеймер: «Проект является продуктом независимой
разработки и не связан с какими-либо компаниями… не является коммерческим продуктом или
официальным выпуском какого-либо стороннего разработчика». При этом библиотека размещена
на `opensource.tbank.ru` и рекомендована к установке в документации T-Bank Dev Portal.

Поэтому в плане она называется **рекомендованным в документации T-Bank SDK**, а не
«официальным SDK». Практических последствий для выбора нет — альтернативы хуже (см. ниже),
но формулировка должна быть точной, чтобы не создавать ложных ожиданий по поддержке.

### Alternatives considered

- **`tinkoff-investments` (старое имя)** — на PyPI отсутствует (404). Отпадает.
- **`tinkoff-invest` (PyPI, 200)** — это сторонняя библиотека `asakharov/tinkoff_invest`,
  не имеющая отношения к рекомендованному SDK. Ложное совпадение имени; не использовать.
- **Собственный gRPC-клиент по .proto** — контроль над зависимостями и отсутствие внешнего
  индекса, но это неделя работы и постоянная поддержка сгенерированного кода ради чтения
  двух методов. Отклонено по Принципу II.
- **REST-контур T-Invest API** — уводит от рекомендованного пути и всё равно требует
  собственного клиента. Отклонено.

### Риск и его снятие

Внешний непубличный индекс — единственная точка отказа сборки. Снятие: версия
пинуется точно (`==1.49.3`), хеши фиксируются в lock-файле, `--extra-index-url`
(не `--index-url`), чтобы остальные зависимости продолжали ставиться с PyPI.
Если `opensource.tbank.ru` окажется недоступен из CI — резервный вариант
вендорить `.whl` в репозиторий обсуждается отдельно, по умолчанию не делается.

## 2. Планировщик фоновой синхронизации

### Decision

**Не использовать APScheduler.** Фоновую синхронизацию реализовать как одну
asyncio-задачу в `Backend-Worker`:

```python
while not stop.is_set():
    interval = await settings_repo.get_interval_seconds()   # чтение при каждом цикле
    await sync_account_state()                              # под общим локом
    await wait_or_stop(interval)
```

### Rationale

- Задача ровно одна, cron-выражения не нужны, персистентность job store не нужна.
- Интервал по FR-031 меняется в рантайме, а SC-012 требует применения к следующему циклу
  **без перезапуска**. В цикле это одна строка (перечитать значение из БД); в APScheduler
  это `reschedule_job` плюс механизм доставки изменения из Backend-API в Worker.
- FR-033 (запрет наложения) в цикле выполняется структурно: следующая итерация не
  начинается, пока не завершилась предыдущая. В APScheduler это отдельные
  `max_instances=1` / `coalesce=True` / `misfire_grace_time`.
- Минус зависимости и минус конфигурационная поверхность (Принцип II).

APScheduler остаётся разумным выбором, когда появятся Daily ML и Intraday Execution ML с
календарными расписаниями. Тогда его и добавим — по фактической потребности.

### Alternatives considered

- **APScheduler** (предложение исходного плана) — рабочее, но избыточно для одной задачи и
  усложняет динамическую смену интервала.
- **Cron в контейнере / внешний scheduler** — новый инфраструктурный компонент ради
  одного таймера. Отклонено.
- **`pg_cron`** — переносит логику приложения в БД, ломает границы контейнеров. Отклонено.

## 3. Как изменение интервала доходит до Worker

### Decision

Worker перечитывает `account_refresh_settings.interval_seconds` из PostgreSQL **в начале
каждого цикла**. Отдельного канала уведомления (REST-вызов из API в Worker, `LISTEN/NOTIFY`,
очередь) не вводится.

### Rationale

Худшая задержка применения нового интервала — один текущий цикл, что удовлетворяет
формулировке SC-012 «применяется к следующему циклу обновления». Ноль дополнительной
инфраструктуры, отсутствие рассинхронизации между источником истины (БД) и планировщиком.

Исходный план этот механизм не описывал вовсе — при хранении настройки в БД и
планировщике в Worker без него FR-031 и SC-012 не выполняются.

### Alternatives considered

- **`POST /internal/reschedule` из Backend-API** — мгновенное применение, но новый контракт
  и новый режим отказа (API дошёл до БД, но не дошёл до Worker → расхождение). Отклонено.
- **PostgreSQL `LISTEN/NOTIFY`** — та же цель, ещё одно постоянное соединение и обработка
  переподключений. Отклонено.

## 4. Дедупликация одновременных синхронизаций (FR-029, FR-033)

### Decision

Два уровня:

1. **In-process**: `asyncio.Lock` в Worker вокруг `sync_account_state()`. Ручной запрос,
   пришедший во время выполняющейся синхронизации, не создаёт второго обращения к брокеру —
   он дожидается текущего и возвращает его результат (`deduplicated: true` в ответе).
2. **Cross-process**: PostgreSQL advisory lock (`pg_try_advisory_lock`) на время
   синхронизации — страховка на случай нескольких реплик Worker или перекрытия
   деплоев.

### Rationale

FR-029 распространяется на ручные и фоновые запросы одновременно, US2 AS5 и US3 AS3
описывают именно конкуренцию двух источников. In-process лока достаточно при одной
реплике; advisory lock стоит две строки и снимает целый класс отказов при
масштабировании. Исходный план требование дедупликации не покрывал.

### Alternatives considered

- **Только in-process lock** — ломается при второй реплике Worker.
- **Очередь задач (Celery/ARQ/Redis)** — новый брокер сообщений и новый контейнер ради
  сериализации одной задачи. Прямо противоречит Принципу II.

## 5. Денежная точность

### Decision

- В домене и persistence — только `decimal.Decimal`, `float` запрещён на всём пути
  «брокер → БД → API → JSON».
- В PostgreSQL: `NUMERIC(28, 9)` для цен, количеств и денежных величин.
- В JSON-контрактах Backend-API денежные и количественные значения передаются
  **строками** (`"362068.00"`), а не числами.
- Округление до копеек — только там, где этого требует представление или бизнес-правило;
  форматирование под русскую локаль (FR-016) выполняет frontend, не backend.

**Статус**: подтверждено владельцем проекта 2026-08-26.

### Rationale

T-Invest API отдаёт `Quotation` / `MoneyValue` как `units` (int64) + `nano` (int32,
1e-9). Точное представление — `units + nano / 1_000_000_000` в `Decimal`.
SC-002 требует совпадения «с точностью до копейки», SC-003 — схождения сумм и долей;
`float` и `JSON number` (double в JS) эти требования нарушают на длинных портфелях.
`NUMERIC(28,9)` сохраняет исходную точность nano без потерь и оставляет запас разрядов для агрегатов.

Исходный план денежную точность не упоминал — это самый дорогой в исправлении дефект,
если он попадёт в схему БД.

### Alternatives considered

- **`NUMERIC(20,2)`** — теряет nano-точность цен и ломает пересчёт стоимости позиции.
- **`NUMERIC(20,9)`** — точность та же, но меньше запас целой части; владелец проекта
  зафиксировал `NUMERIC(28,9)` как значение по умолчанию.
- **Хранить `units`/`nano` парой int** — точно, но каждая агрегация превращается в ручную
  арифметику. Отклонено в пользу `NUMERIC`.
- **JSON-числа вместо строк** — молчаливая потеря точности в JS. Отклонено.

## 6. Частота опроса Backend-API фронтендом

### Decision

Ввести **два независимых интервала** и явно их развести:

| Интервал | Кто | Что делает | Значение |
|---|---|---|---|
| `refresh_interval_seconds` | Backend-Worker | обращается к T-Bank API | настройка пользователя, 60 с по умолчанию, 15–3600 |
| poll-интервал | Frontend (TanStack Query `refetchInterval`) | читает уже сохранённое состояние из Backend-API | `clamp(refresh_interval / 10, 3 c, 30 c)` |

Backend-API возвращает `refresh_interval_seconds` в ответе, frontend вычисляет свой
poll-интервал из него.

### Rationale

SC-010 говорит об **отображаемом** состоянии: «обновляется не реже одного раза за
настроенный интервал, с отклонением не более 10%». Если фронт опрашивает API с тем же
интервалом, что Worker ходит к брокеру, два независимых таймера дают задержку показа до
двух интервалов — SC-010 не выполняется. Опрос сохранённого состояния дёшев (одно чтение
из PostgreSQL, без обращения к брокеру), поэтому опрашивать в 10 раз чаще безопасно, а
отклонение отображения укладывается в 10%.

Исходный план этой развилки не содержал: он описывал один интервал, что при буквальной
реализации нарушает SC-010.

### Alternatives considered

- **SSE / WebSocket push из Backend-API** — идеальная свежесть и ноль лишних запросов, но
  новый транспорт, переподключения и состояние на сервере. Хороший кандидат на будущее,
  избыточен для первой поставки (Принцип II).
- **Один общий интервал** — нарушает SC-010, см. выше.
- **Опрос фронтом = интервал/2** — отклонение до 50%, SC-010 не выполняется.

## 7. Разделение «нет связи с сервером» и «сбой T-Bank API» (FR-037, FR-038)

### Decision

Причина различается **уровнем ответа**, а не полем внутри одного тела:

| Что произошло | Что видит frontend | Состояние UI |
|---|---|---|
| Запрос к Backend-API не завершился (сетевая ошибка, таймаут, 502/503/504 от Nginx) | ошибка транспорта в TanStack Query | «Нет связи с сервером Financial AI» |
| Backend-API ответил 200, в теле `sync.status = "failed"` | успешный ответ с данными | «Не удалось обновить портфель» + время последней успешной синхронизации |
| Backend-API ответил 200, `sync.status = "ok"`, но `sync.is_stale = true` | успешный ответ | «Данные устарели» |

`is_stale` вычисляет **backend** по FR-040 (`max(3 × интервал, 180 с)`), frontend его не
пересчитывает — это соответствует пункту 6 исходного плана («Frontend самостоятельно
ничего о состоянии брокера не вычисляет»).

### Rationale

Различение получается структурно, из самого факта наличия HTTP-ответа, и не требует
отдельного health-опроса или эвристик. Единственное, что frontend добавляет от себя, —
экспоненциальный retry подключения и кнопка немедленного повтора (FR-038, FR-039).

### Alternatives considered

- **Отдельный `GET /api/health` для определения связи** — лишний запрос; отсутствие связи
  и так наблюдается по основному запросу. Health-endpoint остаётся, но для
  Docker healthcheck, а не для UI.
- **Один общий баннер с текстом причины** — отклонено владельцем проекта в сессии
  уточнений (нужны два различимых состояния).

## 8. Структура backend-кода: два контейнера, один Python-проект

### Decision

`Backend-API` и `Backend-Worker` — **два контейнера из одного Python-пакета** `backend/`
с общим `pyproject.toml` и двумя точками входа:

```text
backend-api    → uvicorn financial_ai.api.app:app
backend-worker → uvicorn financial_ai.worker.app:app  (+ фоновая asyncio-задача в lifespan)
```

### Rationale

Оба сервиса используют одни и те же SQLAlchemy-модели, домменные расчёты и настройки.
Разделение на два независимых проекта немедленно требует третьего — общей библиотеки — с
собственной версионностью и публикацией. Один пакет с двумя entrypoint'ами даёт те же
границы контейнеров (архитектурная диаграмма соблюдена: Worker ходит в T-Bank, API — нет),
но без инфраструктуры общей библиотеки. Прямое применение Принципа II.

Разделение на отдельные пакеты выполняется тогда, когда сервисам реально понадобятся
разные зависимости или разный цикл релиза.

### Alternatives considered

- **Два независимых проекта + общий пакет** — правильный конечный вид, преждевременный сейчас.
- **Один контейнер вместо двух** — нарушил бы архитектурную диаграмму и границу
  «Backend-API не ходит в T-Bank». Отклонено.

## 9. Frontend: где TanStack уместен, а где нет

### Decision

| Библиотека | Решение | Обоснование |
|---|---|---|
| **TanStack Query** | использовать | polling, refetch, loading/error/stale state, дедупликация запросов, retry — ровно требования FR-014/015/027/038 |
| **TanStack Table** | использовать | сортировка по любому столбцу с переключением направления (FR-018) — headless, без навязанной вёрстки, дизайн Open Design сохраняется |
| **TanStack Router** | не использовать | в объёме фичи один экран; React Router или отсутствие роутера решают задачу без новой абстракции |
| **TanStack Form** | не использовать | единственный ввод — целое число секунд; контролируемый input + zod-схема проще |
| **TanStack Start / Virtual** | не использовать | SSR не требуется; виртуализация нужна от тысяч строк, портфель на порядки меньше |

### Rationale

Инструкция «в целом инфраструктуру TanStack задействуй, где применима» выполняется по
критерию применимости: Query и Table снимают реальный объём работы, остальные пакеты
добавляют абстракции под несуществующие требования (Принцип II).

## 10. Расхождения с утверждённым дизайном Open Design

Проверен проект «Портфель FINANCIAL AI» (`financial-ai-portfolio.html`, `brand-spec.md`).

**В дизайне есть, а в объёме фичи больше нет** (решение Q4 сессии уточнений):
`connect-broker-cta`, `connect-broker-dialog`, `menuDisconnect` («Отключить брокера»).

**В объёме фичи есть, а в дизайне нет**:

1. элемент настройки интервала автообновления (FR-035, FR-036);
2. состояние «нет связи с сервером Financial AI» (FR-015, FR-038) — индикатор
   `connection-status` в шапке относится к подключению брокера
   («Т-Банк подключён · счёт •• 4821»), а не к связи с сервером.

Существующий универсальный баннер (`bannerTitle` / `bannerText` / `bannerAction`)
переиспользуется для нового состояния, но тексты, иконка и цветовой токен должны быть
утверждены в Open Design.

### Decision

Дизайн-артефакт обновлён в Open Design **до** реализации соответствующих экранов, в рамках
токенов `brand-spec.md`. Задание — [design-update-prompt.md](./design-update-prompt.md).

### Результат проверки (2026-08-26)

Все правки внесены:

- **Настройка интервала**: `refresh-interval-form` с `input[type=number]`,
  `min=15 max=3600 step=1 value=60`, подсказка «Целое число от 15 до 3600 секунд»,
  `aria-invalid` + `intervalError`; при недопустимом вводе сообщается, что прежний интервал
  продолжает действовать (US2 AS4).
- **Действующий интервал** показан в шапке, в меню счёта и в блоке «Действует сейчас»
  (FR-036).
- **Состояние `server-offline`**: инвертированный баннер (`background: var(--fg)`),
  пульсирующая иконка, «Нет связи с сервером Financial AI», действие «Повторить», данные
  помечены как последние известные с возрастом. Отличается от «Не удалось обновить
  портфель» подачей и действием («Повторить запрос к брокеру») — SC-011.
- **Удалены** `connect-broker-cta`, `connect-broker-dialog`, `menuDisconnect`.
- **«Брокер не подключён»** переосмыслено: «Доступ к Т-Банк не сконфигурирован» с
  пояснением для администратора, без действия и без раскрытия токена.
- Семь состояний переключаются в прототипе клавишами 1–7.

**Не переносить из прототипа в реализацию**: хранение интервала в `localStorage` (в
системе это серверная настройка, FR-034) и таймер обновления, равный интервалу
синхронизации (во фронтенде опрос идёт с `clamp(интервал / 10, 3 c, 30 c)`, см. §6).

## 12. Quality gates (Принцип IV) — отсутствовали в исходном плане

| Область | Инструменты |
|---|---|
| Python lint + format | `ruff check`, `ruff format --check` |
| Python types | `mypy` (strict для `financial_ai.domain` и `financial_ai.broker`) |
| Python tests | `pytest`, `pytest-asyncio`, `respx` (внутренний REST), фейковый broker-адаптер |
| Frontend lint + format | `eslint`, `prettier --check` |
| Frontend types | `tsc --noEmit` |
| Frontend tests | `vitest`, `@testing-library/react`, `msw` |
| Миграции | `alembic upgrade head` на чистой БД в CI |

Тестирование обращений к брокеру выполняется **на границе адаптера** (`financial_ai.broker`),
а не мокированием gRPC: адаптер возвращает доменные модели, тесты подставляют фейковую
реализацию его протокола. Это оставляет SDK единственным непокрытым слоем и не привязывает
тесты к его внутреннему устройству.

Песочница T-Invest (`INVEST_GRPC_API_SANDBOX`) может использоваться для ручной проверки
интеграции, но не в автоматических тестах — внешняя зависимость в CI недопустима.

## 13. Накопленный купонный доход по облигациям (найдено при проверке на живом счёте)

### Проблема

Первая же сверка с реальным счётом отклонила ответ брокера: расчётный итог разошёлся с
`total_amount_portfolio` на 13 772,28 ₽ (1,27%). Разбор по категориям показал, что
расхождение точно равно сумме `quantity × current_nkd` по двум позициям ОФЗ.

T-Invest отдаёт по облигации **чистую цену** в `current_price` и накопленный купонный
доход отдельным полем `current_nkd`, но в `total_amount_bonds` и в итог портфеля
включает обе величины.

### Decision

Стоимость позиции считается как `quantity × (current_price + accrued_interest)`.
НКД хранится отдельной колонкой и отдаётся в API, чтобы разницу между «количество ×
цена» и стоимостью можно было объяснить пользователю; в таблице позиций у таких строк
показывается пометка «вкл. НКД».

### Rationale

Без этого не выполняются SC-002 (совпадение с брокером до копейки) и SC-003 (сходимость
сумм и долей) на любом портфеле с облигациями. Сверка с итогом брокера, заложенная в
валидацию (§ 5), обнаружила это на первом же реальном ответе — до того как расхождение
увидел бы пользователь.

### Проверено

На реальном счёте: расчётный итог 1 085 231,42 ₽ против 1 085 231,43 ₽ у брокера
(расхождение в пределах копейки, вызванное округлением nano), сумма долей — ровно
100,000000%.
