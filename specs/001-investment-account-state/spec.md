# Feature Specification: Investment Account State

**Feature Branch**: `feature/investment-account-state`

**Created**: 2026-08-26

**Status**: Clarified

**Input**: User description: "Feature Specification: Investment Account State. 1. Цель — реализовать первый сквозной пользовательский сценарий Financial AI: получение актуального состояния инвестиционного счёта из T-Bank, сохранение его во внутренней БД системы и отображение в web-интерфейсе. Фича должна стать основой для дальнейшего развития раздела портфеля. 2. Пользовательский сценарий — пользователь открывает Financial AI и видит актуальное состояние своего инвестиционного счёта. Отображаемые данные должны соответствовать состоянию, полученному из T-Bank API. Интерфейс должен быть реализован в соответствии с утверждённым дизайном из Open Design."

## Clarifications

### Session 2026-08-26

- Q: Способ авторизации доступа к T-Bank API (FR-021)? → A: Персональный токен Т-Банк Invest с правами только на чтение, передаваемый серверной части через переменную окружения `TBANK_INVEST_READ_TOKEN`. Токен не вводится в интерфейсе, не хранится во внутреннем хранилище системы и не попадает в репозиторий. Итоговое расположение файла конфигурации согласуется отдельно; способ передачи — переменная окружения — зафиксирован.
- Q: Судьба сценария подключения брокера в интерфейсе после выбора серверного токена (FR-020, FR-024)? → A: Исключён из объёма фичи. Факт подключения определяется наличием валидного токена в конфигурации сервера; действия «Подключить Т-Банк» и «Отключить» в интерфейсе не реализуются.
- Q: Один брокерский счёт на пользователя или несколько с выбором активного (FR-025)? → A: Ровно один брокерский счёт. Выбор активного счёта, переключение между счетами и агрегация по нескольким счетам вне объёма фичи.
- Q: Политика обновления состояния счёта (FR-006)? → A: Оба режима одновременно — фоновое автоматическое обновление по интервалу и ручное обновление по требованию пользователя.
- Q: Как задаётся интервал автообновления? → A: Настройкой в веб-интерфейсе: свободный ввод целого числа секунд с валидацией допустимого диапазона; значение по умолчанию — 60 секунд.
- Q: Существует ли в системе пользователь как отдельная сущность (FR-010)? → A: На этом этапе — нет. Есть только токен доступа в конфигурации сервера и ровно один счёт. Таблица пользователей и привязка данных к идентификатору пользователя не вводятся до появления аутентификации.
- Q: Как сигнализировать пользователю обрыв связи? → A: Двумя различимыми состояниями с отдельными сообщениями: «нет связи с сервером Financial AI» и «не удалось обновить портфель» (сбой T-Bank API). В обоих случаях отображаются последние известные данные с их возрастом и временем последней успешной синхронизации.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр актуального состояния инвестиционного счёта (Priority: P1)

Пользователь открывает раздел «Портфель» в Financial AI и сразу видит фактическое состояние своего брокерского счёта в Т-Банке: суммарную стоимость капитала, остаток денежных средств, текущий нереализованный P&L и полный список позиций с количеством, средней ценой, текущей ценой, стоимостью, P&L и долей в портфеле. Рядом с данными указано, на какой момент времени они актуальны.

**Why this priority**: Это и есть целевой сквозной сценарий фичи. Без него ни одна другая история не имеет ценности: автообновление, ручное обновление и обработка сбоев существуют только для того, чтобы пользователь увидел корректное состояние счёта.

**Independent Test**: При наличии подключённого счёта и сохранённого состояния в системе открыть раздел «Портфель» и сверить каждое отображённое значение с состоянием, полученным из T-Bank API. История поставляет самостоятельную ценность даже без остальных.

**Acceptance Scenarios**:

1. **Given** брокерский счёт подключён и в системе есть сохранённое состояние счёта, **When** пользователь открывает раздел «Портфель», **Then** отображаются общая стоимость, денежные средства с долей в портфеле, текущий P&L в абсолютном и процентном выражении, количество позиций и таблица позиций.
2. **Given** пользователь открывает раздел «Портфель», **When** данные ещё загружаются, **Then** отображается состояние загрузки, а не пустой экран и не устаревшие значения без пометки.
3. **Given** состояние счёта отображено, **When** пользователь смотрит на блок актуальности, **Then** он видит возраст данных и точное время последней успешной синхронизации с брокером.
4. **Given** брокерский счёт подключён, но не содержит ни одной позиции и денежных средств, **When** пользователь открывает раздел «Портфель», **Then** отображается состояние «В портфеле пока нет позиций», а суммарные показатели показывают нулевые значения без ложных процентов изменения.
5. **Given** состояние счёта отображено, **When** пользователь сверяет суммы, **Then** сумма стоимостей всех позиций и денежных средств равна отображённой общей стоимости, а сумма долей позиций и денежных средств составляет 100%.

### User Story 2 - Автоматическое поддержание актуальности состояния счёта (Priority: P2)

Пользователь держит раздел «Портфель» открытым и видит, что состояние счёта обновляется само, без его участия: значения и отметка актуальности пересчитываются с заданным интервалом. Частоту обновления пользователь может изменить в интерфейсе.

**Why this priority**: Данные счёта меняются в течение торгового дня, и пользователь не должен поддерживать их свежесть вручную. При этом базовое отображение (P1) работоспособно и без фонового обновления, поэтому история отделима.

**Independent Test**: Открыть раздел «Портфель» с подключённым счётом и, не выполняя никаких действий, убедиться, что по истечении настроенного интервала значения и отметка последней успешной синхронизации обновились; затем изменить интервал в интерфейсе и убедиться, что новая частота применилась.

**Acceptance Scenarios**:

1. **Given** раздел «Портфель» открыт и состояние счёта отображено, **When** истекает настроенный интервал автообновления, **Then** система запрашивает состояние счёта у брокера, сохраняет его и обновляет отображаемые значения и отметку последней успешной синхронизации без действий пользователя.
2. **Given** выполняется автообновление, **When** новые данные отрисованы, **Then** пользовательский контекст не сбрасывается: выбранная сортировка таблицы позиций и позиция прокрутки сохраняются.
3. **Given** настройка интервала обновления отображена со значением по умолчанию 60 секунд, **When** пользователь вводит другое допустимое значение в секундах и сохраняет его, **Then** система сохраняет настройку и применяет новый интервал к последующим автообновлениям без перезапуска системы.
4. **Given** пользователь вводит значение вне допустимого диапазона или не являющееся целым числом секунд, **When** он пытается сохранить настройку, **Then** система отклоняет ввод с понятным объяснением допустимого диапазона, а ранее действовавший интервал продолжает применяться.
5. **Given** автообновление уже выполняется, **When** пользователь в этот же момент запускает обновление вручную, **Then** дублирующий параллельный запрос к брокеру не выполняется.
6. **Given** очередное автообновление завершилось ошибкой, **When** ошибка обработана, **Then** отображается последнее известное состояние с предупреждением, а автообновление не прекращается и повторяет попытку в следующем интервале.

### User Story 3 - Обновление состояния счёта по требованию (Priority: P2)

Пользователь, видя состояние счёта, нажимает «Обновить сейчас» и получает свежие данные из T-Bank API с обновлённой отметкой времени.

**Why this priority**: Данные счёта меняются в течение торгового дня, и пользователю нужен явный контроль над их актуальностью. При этом базовое отображение (P1) работоспособно и без ручного обновления.

**Independent Test**: На отображённом состоянии счёта выполнить обновление и убедиться, что значения и отметка времени пересчитаны по свежему ответу брокера.

**Acceptance Scenarios**:

1. **Given** состояние счёта отображено, **When** пользователь запускает обновление, **Then** отображается индикация загрузки, затем обновлённые значения и новая отметка времени последней синхронизации.
2. **Given** обновление успешно завершено, **When** данные отрисованы, **Then** пользователь получает подтверждение обновления, а сохранённое в системе состояние счёта соответствует показанному.
3. **Given** обновление запущено, **When** пользователь повторно нажимает «Обновить» до завершения текущего запроса, **Then** параллельный дублирующий запрос к брокеру не выполняется.

### User Story 4 - Прозрачность актуальности данных при сбоях брокера и обрыве связи (Priority: P3)

Когда T-Bank API недоступен или вернул ошибку, либо когда интерфейс потерял связь с сервером Financial AI, пользователь всё равно видит последнее известное состояние счёта и явное предупреждение о том, что данные не свежие, на какой момент они актуальны и какая именно связь нарушена.

**Why this priority**: Повышает доверие к данным и предотвращает финансовые решения по неверно интерпретированным цифрам, но не блокирует основной сценарий при работающем брокере.

**Independent Test**: Смоделировать по отдельности недоступность T-Bank API и обрыв связи интерфейса с сервером и убедиться, что в каждом случае показывается последнее известное состояние с предупреждением, однозначно называющим причину, а не пустой экран или необъяснённая ошибка.

**Acceptance Scenarios**:

1. **Given** в системе есть сохранённое состояние счёта, **When** запрос к брокеру завершился ошибкой или таймаутом, **Then** отображается последнее известное состояние, предупреждение «Не удалось обновить портфель» с указанием времени последней успешной синхронизации и возможностью повторить обновление.
2. **Given** в системе есть сохранённое состояние счёта, **When** возраст данных превысил допустимый порог свежести, **Then** отображается предупреждение об устаревших данных с указанием возраста и времени последней успешной синхронизации.
3. **Given** запрос к брокеру завершился ошибкой, **When** отображается предупреждение, **Then** сохранённое состояние счёта не затирается частичными или пустыми данными.
4. **Given** брокер подключён, но в системе ещё нет ни одного успешно сохранённого состояния, **When** первый запрос к брокеру завершился ошибкой, **Then** пользователь видит понятное сообщение об ошибке и действие для повторной попытки, а не нулевые суммы, выдаваемые за фактические.
5. **Given** отображается предупреждение о несвежих данных, **When** очередное обновление прошло успешно, **Then** предупреждение исчезает и статус актуальности возвращается к нормальному.
6. **Given** состояние счёта отображено, **When** интерфейс теряет связь с сервером Financial AI, **Then** отображается предупреждение «Нет связи с сервером» — отличное по формулировке от предупреждения о сбое брокера, — отображаемые данные помечаются как последние известные с указанием их возраста, а система автоматически повторяет попытки восстановить связь и предоставляет действие для немедленного повтора.
7. **Given** отображается предупреждение об отсутствии связи с сервером, **When** связь восстановлена и данные успешно получены, **Then** предупреждение исчезает автоматически, без перезагрузки страницы пользователем.

### User Story 5 - Разбор состава портфеля (Priority: P3)

Пользователь сортирует таблицу позиций по интересующему его столбцу (например, по доле в портфеле или по P&L), чтобы быстро понять структуру капитала и найти отклонения.

**Why this priority**: Улучшает анализ, но состав портфеля читаем и в сортировке по умолчанию, поэтому история не критична для первой поставки.

**Independent Test**: На отображённой таблице позиций переключить сортировку по каждому поддерживаемому столбцу и проверить корректность порядка и индикации направления.

**Acceptance Scenarios**:

1. **Given** таблица позиций отображена, **When** пользователь выбирает столбец для сортировки, **Then** строки переупорядочиваются по этому столбцу и отображается направление сортировки.
2. **Given** таблица отсортирована по столбцу, **When** пользователь повторно выбирает тот же столбец, **Then** направление сортировки меняется на противоположное.
3. **Given** пользователь не менял сортировку, **When** таблица отображена впервые, **Then** позиции отсортированы по убыванию доли в портфеле.

---

### Edge Cases

- Что происходит, когда счёт содержит позиции, но нулевой остаток денежных средств — доля денежных средств отображается как 0% без деления на ноль.
- Как система ведёт себя, когда суммарная средняя стоимость позиций равна нулю (например, позиции получены в результате внешнего зачисления без цены приобретения) — процент P&L не рассчитывается и не показывается как ложный ноль.
- Что происходит, когда брокер возвращает позицию по инструменту, ранее не встречавшемуся системе — позиция отображается по идентификатору инструмента, отсутствие человекочитаемого названия не блокирует отображение остальных данных.
- Как система ведёт себя, когда брокер возвращает позицию с отрицательным количеством (короткая позиция) — количество, стоимость и доля отображаются корректно, без искажения суммарных показателей.
- Что происходит, когда ответ брокера не проходит валидацию (несогласованные суммы, отсутствующие обязательные поля) — состояние не сохраняется как актуальное, пользователь видит предупреждение о невозможности обновления.
- Как система ведёт себя при отзыве или истечении срока действия доступа к T-Bank API — пользователь получает понятное сообщение о необходимости переподключить брокера, а не техническую ошибку.
- Что происходит при обращении к T-Bank API в нерабочие часы биржи — отображается последнее известное состояние с корректной отметкой времени, отсутствие движения цен не трактуется как сбой.
- Как система ведёт себя при превышении лимитов запросов к T-Bank API — обновление откладывается с понятным пользователю объяснением, повторные запросы не усугубляют превышение лимита.
- Что происходит, когда в портфеле очень много позиций — таблица остаётся читаемой, а время отображения раздела не выходит за границы, заданные в Success Criteria.
- Что происходит, когда очередное автообновление не успевает завершиться до наступления следующего интервала — новый фоновый запрос не запускается поверх незавершённого, пропущенные интервалы не накапливаются в очередь.
- Как система ведёт себя, когда пользователь меняет интервал автообновления во время выполняющегося обновления — текущее обновление завершается штатно, новый интервал применяется к следующему циклу.
- Что происходит при обрыве связи с сервером во время выполнения ручного обновления — пользователь видит предупреждение об отсутствии связи, а не подтверждение успешного обновления, и сохранённое состояние не считается обновлённым.
- Как система различает недоступность сервера Financial AI и недоступность T-Bank API — эти причины никогда не подменяют друг друга в сообщении пользователю.
- Как система считает стоимость облигации — в неё включается накопленный купонный доход (НКД), как это делает брокер: иначе сумма позиций расходится с итогом брокера и суммы в интерфейсе не сходятся.
- Что происходит, когда токен доступа к T-Bank API не задан, пуст или отклонён брокером — отображается состояние «брокер не подключён» с указанием, что доступ не сконфигурирован, без раскрытия значения токена.

## Requirements *(mandatory)*

### Functional Requirements

**Получение данных от брокера**

- **FR-001**: Система ДОЛЖНА получать актуальное состояние инвестиционного счёта пользователя из T-Bank API, включая денежный остаток и полный перечень позиций.
- **FR-002**: Система ДОЛЖНА получать по каждой позиции: идентификатор инструмента, человекочитаемое название, количество, среднюю цену приобретения и текущую цену.
- **FR-003**: Система ДОЛЖНА фиксировать момент времени, на который получено состояние счёта, и использовать его как единственный источник отображаемой актуальности.
- **FR-004**: Система ДОЛЖНА валидировать полученное от брокера состояние на полноту и внутреннюю согласованность до его сохранения как актуального.
- **FR-005**: Система ДОЛЖНА выполнять обращения к T-Bank API исключительно в режиме чтения; фича НЕ ДОЛЖНА инициировать торговые операции или изменять состояние счёта у брокера.
- **FR-006**: Система ДОЛЖНА обновлять состояние счёта в двух режимах одновременно: автоматически в фоне с заданным интервалом и по явному запросу пользователя.
- **FR-031**: Система ДОЛЖНА выполнять фоновое автообновление с интервалом, заданным пользовательской настройкой; значение по умолчанию — 60 секунд, допустимый диапазон — от 15 до 3600 секунд включительно.
- **FR-032**: Система ДОЛЖНА продолжать фоновое автообновление после неуспешной попытки синхронизации и НЕ ДОЛЖНА прекращать его из-за ошибок брокера.
- **FR-033**: Система ДОЛЖНА исключать наложение фоновых обновлений: новое фоновое обращение к брокеру НЕ ДОЛЖНО запускаться, пока предыдущее не завершилось, а пропущенные интервалы НЕ ДОЛЖНЫ накапливаться в очередь.

**Хранение состояния**

- **FR-007**: Система ДОЛЖНА сохранять полученное состояние счёта во внутреннем хранилище, чтобы интерфейс мог отображать его без синхронного обращения к брокеру.
- **FR-008**: Система ДОЛЖНА сохранять состояние счёта атомарно: частично полученное или не прошедшее валидацию состояние НЕ ДОЛЖНО заменять ранее сохранённое.
- **FR-009**: Система ДОЛЖНА сохранять вместе с состоянием счёта время его получения от брокера и статус последней попытки синхронизации (успех или ошибка с причиной).
- **FR-010**: Система ДОЛЖНА хранить состояние счёта в привязке к брокерскому счёту и НЕ ДОЛЖНА раскрывать его за пределами установки, обслуживающей этот счёт. На текущем этапе пользователь как отдельная сущность в системе отсутствует: доступ определяется единственным сконфигурированным токеном и единственным счётом (FR-021, FR-025). Привязка данных к идентификатору пользователя вводится вместе с аутентификацией и в объём фичи не входит.
- **FR-034**: Система ДОЛЖНА сохранять настройку интервала автообновления во внутреннем хранилище так, чтобы она сохранялась между сессиями пользователя и перезапусками системы.

**Отображение**

- **FR-011**: Система ДОЛЖНА отображать сводные показатели капитала: общую стоимость счёта, остаток денежных средств с их долей в портфеле, текущий нереализованный P&L в абсолютном и процентном выражении относительно средней стоимости позиций, количество позиций.
- **FR-012**: Система ДОЛЖНА отображать таблицу позиций со столбцами: инструмент (тикер и название), количество, средняя цена, текущая цена, стоимость, P&L, доля в портфеле.
- **FR-013**: Система ДОЛЖНА визуально различать положительный и отрицательный P&L.
- **FR-014**: Система ДОЛЖНА отображать возраст данных и точное время последней успешной синхронизации с брокером в каждом состоянии, где данные показаны.
- **FR-015**: Система ДОЛЖНА поддерживать и визуально различать состояния раздела: загрузка, брокер не подключён, портфель пуст, данные актуальны, данные устарели, ошибка синхронизации с брокером, нет связи с сервером Financial AI.
- **FR-035**: Система ДОЛЖНА предоставлять в интерфейсе настройку интервала автообновления в виде ввода целого числа секунд с явно указанным допустимым диапазоном, валидацией ввода и понятным сообщением при недопустимом значении.
- **FR-036**: Система ДОЛЖНА отображать текущий действующий интервал автообновления, чтобы пользователь понимал, с какой частотой обновляются данные.
- **FR-016**: Система ДОЛЖНА отображать все денежные значения в рублях с разделителями разрядов согласно русской локали, а количественные и ценовые значения — в формате, заданном утверждённым дизайном.
- **FR-017**: Интерфейс ДОЛЖЕН соответствовать утверждённому дизайну Open Design (проект «Портфель FINANCIAL AI»): структуре экрана, составу и порядку показателей, набору состояний, типографике и цветовым токенам, заданным в `brand-spec.md`.
- **FR-018**: Пользователи ДОЛЖНЫ иметь возможность сортировать таблицу позиций по любому из отображаемых столбцов с переключением направления сортировки; сортировка по умолчанию — убывание доли в портфеле.
- **FR-019**: Раздел ДОЛЖЕН оставаться пригодным для использования на экранах разных размеров, включая мобильные, в соответствии с адаптивным поведением утверждённого дизайна.

**Подключение брокера**

- **FR-020**: Система ДОЛЖНА определять факт подключения брокерского счёта по наличию валидного токена доступа в конфигурации серверной части; подключение и отключение брокера через интерфейс в объём фичи НЕ ВХОДЯТ.
- **FR-021**: Система ДОЛЖНА обращаться к T-Bank Invest API с персональным токеном, имеющим права только на чтение, получая его на стороне сервера из переменной окружения `TBANK_INVEST_READ_TOKEN`. Токен НЕ ДОЛЖЕН вводиться в интерфейсе, храниться во внутреннем хранилище системы или попадать в репозиторий.
- **FR-022**: Система ДОЛЖНА отображать идентификацию подключённого счёта только в маскированном виде и НЕ ДОЛЖНА показывать полный номер договора или credentials в интерфейсе.
- **FR-023**: Система ДОЛЖНА хранить учётные данные доступа к T-Bank API вне исходного кода и вне репозитория, в защищённом виде, и НЕ ДОЛЖНА выводить их в логи, сообщения об ошибках и диагностику.
- **FR-024**: Система ДОЛЖНА при отсутствующем, пустом или отклонённом брокером токене прекращать обращения к T-Bank API, отображать состояние «брокер не подключён» с указанием, что доступ не сконфигурирован, и НЕ ДОЛЖНА раскрывать значение токена в интерфейсе, логах и сообщениях об ошибках.
- **FR-025**: Система ДОЛЖНА поддерживать ровно один брокерский счёт Т-Банк. Выбор активного счёта, переключение между счетами и агрегация показателей по нескольким счетам в объём фичи НЕ ВХОДЯТ; при наличии у пользователя нескольких счетов у брокера используется единственный сконфигурированный счёт.

**Обработка ошибок и устойчивость**

- **FR-026**: Система ДОЛЖНА при недоступности или ошибке T-Bank API отображать последнее успешно сохранённое состояние счёта с явным предупреждением и указанием времени его получения.
- **FR-027**: Система ДОЛЖНА предоставлять пользователю действие для повторной попытки обновления в состояниях «данные устарели» и «ошибка синхронизации».
- **FR-028**: Система ДОЛЖНА формулировать пользовательские сообщения об ошибках понятным языком, без технических деталей ответа брокера.
- **FR-029**: Система ДОЛЖНА исключать одновременное выполнение нескольких запросов состояния одного и того же счёта независимо от того, инициированы они пользователем или фоновым автообновлением.
- **FR-030**: Система ДОЛЖНА фиксировать факт и причину неуспешной синхронизации для диагностики, не раскрывая при этом чувствительных данных.
- **FR-037**: Система ДОЛЖНА различать и по-разному сигнализировать пользователю два класса сбоев: отсутствие связи интерфейса с сервером Financial AI и невозможность получить данные от T-Bank API. Одна причина НЕ ДОЛЖНА выдаваться за другую.
- **FR-038**: Система ДОЛЖНА при отсутствии связи с сервером Financial AI отображать явное предупреждение об этом, помечать отображаемые данные как последние известные с указанием их возраста, автоматически повторять попытки восстановления связи и предоставлять действие для немедленного повтора.
- **FR-039**: Система ДОЛЖНА автоматически снимать предупреждение об отсутствии связи после её восстановления и успешного получения данных, без перезагрузки страницы пользователем.
- **FR-040**: Система ДОЛЖНА считать данные устаревшими, когда возраст последнего успешно сохранённого состояния превышает наибольшее из двух значений: трёхкратный действующий интервал автообновления и 180 секунд.

### Key Entities

- **Пользователь**: владелец счёта в Financial AI; определяет границу видимости данных портфеля.
- **Брокерское подключение**: связь пользователя с брокером Т-Банк; хранит статус подключения (доступ сконфигурирован и принят брокером либо нет), маскированную идентификацию счёта и время последнего успешного обращения. Учётные данные доступа в составе сущности НЕ хранятся — токен предоставляется конфигурацией сервера.
- **Настройка обновления**: пользовательская настройка частоты фонового обновления; интервал в секундах, значение по умолчанию и время последнего изменения.
- **Инвестиционный счёт**: брокерский счёт пользователя в Т-Банке; идентификатор счёта, отображаемое название, валюта счёта; связан с брокерским подключением.
- **Состояние счёта (снимок)**: зафиксированное на момент времени состояние счёта; общая стоимость, остаток денежных средств, суммарный нереализованный P&L в абсолютном и процентном выражении, момент получения от брокера, статус синхронизации; содержит набор позиций.
- **Позиция**: часть состояния счёта, соответствующая одному инструменту; идентификатор инструмента, количество, средняя цена приобретения, текущая цена, стоимость, нереализованный P&L, доля в портфеле.
- **Инструмент**: торгуемый актив; идентификатор, тикер, человекочитаемое название, тип актива, валюта.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В 95% открытий раздела «Портфель» пользователь видит состояние счёта или явное состояние загрузки менее чем за 2 секунды.
- **SC-002**: Отображаемое состояние счёта полностью соответствует состоянию, полученному от брокера: количество и состав позиций совпадают на 100%, а денежные значения совпадают с точностью до копейки.
- **SC-003**: Сумма стоимостей позиций и денежных средств равна отображаемой общей стоимости счёта, а сумма долей составляет 100% с погрешностью округления не более 0,1 процентного пункта в 100% проверок.
- **SC-004**: Обновление состояния по требованию пользователя завершается за время не более 5 секунд в 95% случаев.
- **SC-005**: При недоступности брокера в 100% случаев пользователь видит последнее известное состояние с указанием его возраста, а не пустой экран, нули или необъяснённую ошибку.
- **SC-006**: Во всех состояниях, где показаны данные счёта, возраст данных указан явно — 100% состояний.
- **SC-007**: Все семь состояний раздела, определённых утверждённым дизайном — загрузка, брокер не подключён, портфель пуст, данные актуальны, данные устарели, ошибка синхронизации с брокером, нет связи с сервером, — реализованы и визуально соответствуют ему при дизайн-ревью.
- **SC-008**: Пользователь, впервые открывший Financial AI с подключённым счётом, без подсказок определяет общую стоимость капитала, текущий P&L и актуальность данных — успех у 90% участников проверки.
- **SC-009**: Ни в одном журнале, сообщении об ошибке или ответе интерфейса не встречаются учётные данные доступа к брокеру или полный номер договора — 0 вхождений при проверке.
- **SC-010**: При доступном брокере отображаемое состояние счёта обновляется без действий пользователя не реже одного раза за настроенный интервал, с отклонением не более 10% от интервала в 95% циклов.
- **SC-011**: В 100% смоделированных обрывов связи с сервером и в 100% смоделированных сбоев T-Bank API пользователь видит различающиеся сообщения, однозначно указывающие на действительную причину.
- **SC-012**: Изменённый пользователем интервал автообновления применяется к следующему циклу обновления без перезапуска системы в 100% проверок и сохраняется после перезагрузки страницы.

## Assumptions

- Фича охватывает исключительно чтение и отображение состояния инвестиционного счёта. Торговые операции, ML-ранжирование, целевые позиции и исполнение сделок находятся вне её объёма, несмотря на присутствие соответствующих компонентов на целевой архитектурной диаграмме (`source/Diagramma_koneynerov_FinAI.svg`).
- Отображаемый P&L является нереализованным и рассчитывается относительно средней цены приобретения позиции, как показано в утверждённом дизайне («+1,29% к средней стоимости»). Реализованный P&L, налоговый учёт и историческая доходность вне объёма фичи.
- Все денежные показатели отображаются в рублях. Мультивалютные остатки и позиции в иностранной валюте не входят в объём первой поставки; при их появлении в ответе брокера они не должны нарушать отображение остальных данных.
- История изменения состояния счёта (графики динамики капитала, сравнение с прошлыми периодами) вне объёма фичи. Хранение снимков состояния при этом не должно исключать такую историю в дальнейшем.
- Аутентификация пользователя в самом Financial AI не входит в объём фичи и на этом этапе отсутствует: система обслуживает один счёт, доступ к которому определяется единственным токеном в конфигурации сервера. Многопользовательский режим и разграничение доступа появятся вместе с аутентификацией.
- Демонстрационные значения из прототипа Open Design («Демонстрационные данные», позиции SBER, LKOH, YDEX, ОФЗ 26238, TMM0) являются иллюстрацией вёрстки, а не требованием; реализация отображает фактические данные брокера.
- Порог устаревания данных выведен из выбранной политики обновления и зафиксирован в FR-040: наибольшее из трёхкратного действующего интервала автообновления и 180 секунд. Нижняя граница в 180 секунд не даёт предупреждению об устаревании срабатывать ложно при малых интервалах.
- Допустимый диапазон интервала автообновления (15–3600 секунд, FR-031) выбран как компромисс между свежестью данных и лимитами запросов T-Bank Invest API; конкретные границы подтверждаются на этапе планирования по фактическим лимитам API.
- Подключение и отключение брокера через интерфейс вне объёма фичи: доступ к T-Bank API конфигурируется на стороне сервера (FR-020, FR-021). Диалог подключения из утверждённого дизайна Open Design реализуется позже, когда появится пользовательское подключение брокера; состояние «Брокер не подключён» при этом используется по назначению — как индикация несконфигурированного доступа.
- Итоговое расположение файла с переменными окружения согласуется отдельно и не влияет на требования: фича полагается только на то, что токен доступен процессу серверной части как переменная окружения `TBANK_INVEST_READ_TOKEN`.
- Данные предоставляются T-Bank Invest API; доступность, лимиты запросов и состав полей этого API являются внешним ограничением фичи.
- Раздел «Портфель» является точкой входа для дальнейшего развития портфельной функциональности, поэтому модель хранения состояния счёта должна допускать расширение без переписывания, но не должна включать абстракции под ещё не заявленные требования (Принцип II Constitution).

## Dependencies

- Доступ к T-Bank Invest API с правами чтения состояния брокерского счёта.
- Утверждённый дизайн Open Design, проект «Портфель FINANCIAL AI» (`financial-ai-portfolio.html`, `brand-spec.md`) — источник требований к интерфейсу.
- Внутреннее хранилище системы для сохранения состояния счёта.
- Персональный токен Т-Банк Invest с правами только на чтение, доступный процессу серверной части через переменную окружения `TBANK_INVEST_READ_TOKEN` (Принцип VII Constitution).
