# Архитектура системы

Описание системы Financial AI: из чего она состоит, кто с кем взаимодействует, где
проходят границы ответственности и что из этого уже реализовано.

Каноном состава компонентов является диаграмма контейнеров
[`container-diagram.svg`](./container-diagram.svg); этот документ — её описание. При
расхождении верна диаграмма, а расхождение либо устраняется, либо явно фиксируется в
разделе «Отступления развёртывания».

---

## 1. Назначение

Платформа для AI-assisted управления инвестиционным портфелем и торговли на российском
фондовом рынке.

Целевая цепочка от данных до сделки:

```text
рыночные и справочные данные
        ↓
     Daily ML              →  ранжирование активов
        ↓
portfolio / target-position logic
        ↓
Intraday Execution ML
        ↓
   исполнение сделок       →  брокер
        ↓
ордера / сделки / позиции
        ↓
Backend / PostgreSQL / Frontend
```

Система развивается поэтапно. **Наличие компонента на диаграмме не означает, что его
функциональность должна быть реализована сейчас.** Диаграмма фиксирует границы
ответственности, а не план работ.

## 4. Взаимодействия

Подписи связей взяты с диаграммы — это канон, а не пересказ:

| От | К | Подпись на диаграмме |
|---|---|---|
| Пользователь | Frontend | Взаимодействие с интерфейсом |
| Nginx | Frontend | Отдаёт статику `[http]` |
| Frontend | Nginx | Отправляет запросы `[http]` |
| Nginx | Backend-API | Перенаправляет запросы `[REST]` |
| Backend-API | Backend-Worker | Команды и состояние задач `[REST]` |
| Backend-API / Worker | PostgreSQL | Чтение / Запись `[SQL]` |
| Backend | Daily ML | **Запуск inference / получение scores `[REST]`** |
| Backend | Intraday Execution ML | Execution state / decision `[REST]` |
| Backend-Worker | T-Bank | Market Data, Orders, Fills, Positions `[gRPC/TLS]` |
| Backend | MOEX | Загрузка исторических и рыночных данных `[REST]` |

Обратите внимание на строку про Daily ML: **REST-интерфейс к звену ранжирования заложен
в канон изначально**. Эмулятор этого звена реализует именно его, а не вводит новое
соглашение.

## 5. Границы ответственности

Правила, нарушение которых является архитектурной ошибкой, а не стилистической:

- **К брокеру ходит только `backend-worker`.** `backend-api` не обращается к T-Bank ни
  при каких условиях.
- **Токен брокера передаётся только контейнеру `backend-worker`.** Его нет в окружении
  ни `backend-api`, ни `frontend`. Задаётся в `deployments/docker-compose/.env`
  **без кавычек**: значение в кавычках уходит к брокеру вместе с ними и отклоняется.
- **Внутренний REST worker'а наружу не проксируется.** Его единственный клиент —
  `backend-api`.
- **Токен создаётся с правами только на чтение** — система не инициирует торговых
  операций.
- **Оркестрация ранжирования принадлежит платформе, а не звену.** Планирование,
  очередь, идемпотентность, повторы и история живут в `backend-worker`; звено получает
  вход и возвращает порядок активов. Замена эмулятора настоящей моделью не должна
  затрагивать ничего из перечисленного.
- **История прогонов читается из хранилища, а не через worker.** Она переживает
  удаление набора и перезапуск сборщика; состояние планировщика — нет.
- **План портфеля считает `backend-api`.** Все его входы уже в хранилище: сохранённое
  ранжирование, состояние счёта, цены закрытия, размеры лотов. Граница прежняя — worker
  ходит наружу, api считает по сохранённому.
- **Расчёт плана портфель не меняет.** Заявок он не выставляет и к брокеру не
  обращается; маршрутов исполнения не существует.

## 6. Потоки данных

Состояние счёта:

```text
T-Bank Invest API → backend-worker → PostgreSQL → backend-api → frontend
```

Ручное обновление:

```text
frontend → backend-api → (внутренний REST) backend-worker → T-Bank Invest API
```

Рыночные данные и ранжирование:

```text
MOEX → backend-worker → PostgreSQL → набор входных данных → Daily ML → порядок активов
```

Раз в торговую сессию, после её закрытия. Календарь TQBR решает, была ли сессия.
Набор неизменяем и опознан дайджестом: тот же дайджест — то же ранжирование, и
постфактум видно, на каких данных оно получено.

**Простой переживается, но не автоматически.** Порядок шагов в ежедневном цикле такой:

```text
календарь → текущая сессия → материализация набора → ранжирование
```

**Календарь стоит первым, и это не формальность.** Пропущенные сессии вычисляются как
разность календаря и собранного, то есть по **сохранённому** календарю. Пока он не
обновлён, новых дат в нём нет, работы не видно — и календарь не обновляется. Замкнутый
круг: после простоя система честно, но бесполезно стоит на старой границе. Разрывает его
`market_data/advance.py`, который синхронизирует календарь, определяет последнюю
**закрытую** сессию и собирает недостающие.

Спрашивается календарь не чаще раза в сутки: тик планировщика — раз в минуту, новые
торговые дни появляются раз в день, и обращение на каждый тик было бы тысячей запросов к
бирже ни за чем. Отметка «сегодня уже спрашивали» лежит в таблице исходов сбора, а не в
памяти процесса — перезапуск её не теряет.

**Недостающей считается любая закрытая сессия окна без собранных котировок** — и
отставание границы, и пропуск внутри окна. Прежде список считался как «дни после
последнего собранного», и дыра посреди окна не попадала в него вовсе: ранжирование из-за
неё не запускалось, а причина не была видна. Незакрытая сессия не собирается ни
автоматически, ни по команде человека — правило одно на оба пути.

**Автоматический сбор останавливается из интерфейса.** Устройство повторяет паузу
ранжирования: состояние в процессе сборщика, по умолчанию сбор идёт, перезапуск возвращает
его в работу. Переключатели разные, и пауза ранжирования сбор данных не останавливает.

**Разрыв собирается целиком за один проход**, а не нарезается по несколько сессий за
тик: нарезка — тот же автоматический догон, только растянутый на минуты. Глубина
ограничена окном догона — сессия старше него в набор не попадёт. Плата принята осознанно:
после долгого простоя восстановление обращается к бирже столько раз, сколько сессий
пропущено. Предел возвращается числом в `MARKET_DATA_STARTUP_RECOVERY_MAX_SESSIONS`; при
разрыве сверх него не собирается ничего, дыра показывается человеку и закрывается
управляемым догоном.

Догона в этом ряду **нет**: он стал управляемой фоновой задачей внутри того же процесса и
стартует только по команде человека — маршрутами внутреннего интерфейса worker'а
(`POST/GET/DELETE /internal/catchup`), рядом с уже существующим `/internal/sync`. Команда
`market_data.cli` — тонкий клиент над ними; интерфейс, когда появится, подключится сюда же.

Причина в наблюдении, а не в предпочтении: автоматический догон однажды ушёл на 2909
обращений к бирже без спроса и без возможности вмешаться. Управление не выставляется
наружу — у контейнера `backend-worker` нет проброса портов.

Состояние задания живёт **в процессе**, а не в хранилище: перезапуск снимает «идёт» сам
собой, и зависшего состояния не бывает по устройству. Что собрано на самом деле — видно по
данным: пропущенные сессии вычисляются как разность календаря и собранного, а не берутся
из отметки «последняя собранная дата». Глубина догона ограничена окном набора.

Рядом живёт сводка состояния (`GET /internal/coverage`): по каждой группе источников —
покрытие в сессиях и доля строк со значениями. Два числа, а не одно, потому что группа
бывает полностью покрыта и при этом пуста.

Что догнать не удалось, объявляется модели вместе с набором: в рядах пропуск выглядит
одинаково и когда бумага не торговалась, и когда за день не ходили на биржу, а различить
эти случаи может только отправитель.

### Жизненный цикл ранжирования

Цепочка одна для трёх случаев — вечерний прогон, восстановление после перезапуска и
разбор накопившегося отставания:

```text
сессия закрылась → данные собраны → полнота обязательного входа проверена →
набор материализован → прогон создан → ранжирование получено → результат сохранён →
дата успешного ранжирования продвинулась
```

Прогон, в отличие от задания догона, **хранится**: догон это процесс, и его состояние
осмысленно только пока он идёт, а прогон — принятое решение, и оно остаётся фактом.
Отсюда обратное правило: `running`, обнаруженный при старте, означает обрыв и переводится
в `failed` — обработчик один, держать запись больше некому.

Идентичность прогона — `asof_date + dataset_digest + model_id + model_version`. Успешный
прогон с тем же ключом означает отсутствие работы; одновременность исключается
advisory-блокировкой PostgreSQL, конкурентное создание — уникальным индексом.

Состояние данных и состояние модели — **две разные даты**. Их расхождение и есть
отставание; свести их в одну означало бы спрятать его.

### План портфеля

```text
сохранённое ранжирование + состояние счёта + цены закрытия + размеры лотов
    → правило распределения → целевые позиции → разница к текущим
```

Между весами и исполнением в исследовательском репозитории разрыв: ребалансировка
оперирует дробными акциями, а модуль исполнения принимает готовое целое количество и
размер лота как обязательные аргументы. Этот разрыв закрывает платформа — округлением до
лота, с ценой закрытия названной сессии и размером лота, собранным с биржи.

Портфельного слоя, принимающего решения самостоятельно, по-прежнему нет: план — это
утверждение о желаемом составе счёта, а не приказ.

## 7. Отступления развёртывания от диаграммы

Отступления фиксируются здесь намеренно: диаграмма остаётся каноном, но развёртывание от
неё отличается, и это различие не должно обнаруживаться заново при каждом чтении.

| Диаграмма | Развёртывание | Причина |
|---|---|---|
| `Nginx` — отдельный контейнер | nginx работает внутри образа `frontend` (multi-stage: сборка Node → runtime `nginx:alpine`) | перед единственным SPA второй проксирующий слой добавляет сервис и volume, не давая ничего. Решение владельца проекта от 2026-08-26. Разделение вернётся, когда за nginx появится больше одного upstream'а |
| `Daily ML` — контейнер инференса | контейнер `daily-ml-emulator` с вымышленными скорами | настоящей модели ещё нет; эмулятор позволяет поднимать стенд целиком и фиксирует форму контракта заранее. Это **временный стенд-заместитель**, а не реализация компонента: с появлением модели он удаляется целиком |
| Связи `Backend-Worker → набор → Daily ML` на диаграмме нет | том с неизменяемыми наборами, доступный обоим | Ряды в теле запроса не идут: окно в 314 сессий — около 5,9 МБ, из которых новой является одна сессия. Это **не** доступ к хранилищу: набор неизменяем, опознан дайджестом, не имеет ни схемы, ни реквизитов доступа и не может молча измениться. Диаграмма дополнена 2026-09-03: элемент «Набор входных данных» и обе связи на ней есть. Осталось расхождение в подписи — связь `Backend-Worker → набор` подписана `[SQL]`, хотя набор это файлы JSON на общем томе; принято владельцем как есть, правится в draw.io |
| Связь `Backend → MOEX` — одна | к бирже идут **два разных** обмена: биржевой интерфейс данных (`iss.moex.com`, JSON, единица обращения — дата) и форма на сайте биржи (`www.moex.com`, HTML, единица обращения — инструмент и дата) | позиций ФИЗ и ЮР по фьючерсам в биржевом интерфейсе нет ни в каком разделе. Внешняя система та же, контейнеров и связей не прибавляется, поэтому каноническая диаграмма не меняется; но общий HTTP-слой ISS сюда не подходит — другой хост, другой протокол обмена, другой формат ответа. Обоснование — `specs/005-market-data-control/plan.md`, Complexity Tracking |

Протокол обращения к T-Bank на диаграмме приведён к фактическому — gRPC.

## 9. Стек

| Слой | Решение |
|---|---|
| Backend | Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), Alembic, asyncpg, `t-tech-investments`, менеджер пакетов `uv` |
| Frontend | TypeScript, React 19, Vite, Node 22 LTS, Feature-Sliced Design, TanStack Query и Table, менеджер пакетов `pnpm` |
| Эмулятор Daily ML | Python 3.12, FastAPI, `uv` — отдельный проект, без зависимостей backend |
| Инфраструктура | PostgreSQL 17, Docker Compose, nginx внутри образа frontend |

`backend-api` и `backend-worker` собираются из **одного** Python-пакета `backend/` с
двумя точками входа и разворачиваются как два контейнера.
